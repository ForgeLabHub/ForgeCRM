# Развёртывание ForgeCRM на blitz.cloud

Это руководство разворачивает работающий ForgeCRM (API + фоновый воркер +
веб-интерфейс) на бесплатном тарифе blitz.cloud, а также на любом хосте, который
собирает корень репозитория.

## Что где работает

ForgeCRM — это одна сборка контейнера, которая содержит три вещи:

1. **API** (`forgecrm-api`) — HTTP-сервер и веб-интерфейс, который он обслуживает.
2. **Воркер** (`forgecrm-worker`) — фоновый процесс: задания импорта/экспорта,
   разбор outbox, доставка вебхуков, планировщик workflow и хранение.
3. **Веб-интерфейс** — собранное React-приложение (SPA), обслуживаемое API из
   `/app/public`. Один адрес отвечает и на API, и на UI, в одном источнике,
   поэтому cookie сессии и двойная отправка CSRF работают без CORS.

Образ собирается **корневым `Dockerfile`**. Корневой `docker-compose.yml`
объявляет две части, `api` и `worker`, которые собирают тот же образ и запускают
разные точки входа. blitz.cloud читает compose-файл, предлагает эти две части и
запускает их как одно приложение.

> **Не добавляйте `# syntax=docker/dockerfile:1` в корневой `Dockerfile`.**
> Эта директива заставляет сборщик сначала скачать образ frontend BuildKit. Хост,
> который не может его достать, падает на самой первой строке файла и после этого
> переходит на собственный («managed») `Dockerfile` — без диспетчера
> `forgecrm-entrypoint`. Тогда часть **worker** запускает второй API и ни одно
> фоновое задание не обрабатывается. Ни один из Dockerfile проекта не использует
> возможностей, доступных только BuildKit, поэтому директива не нужна.
> `TestDockerfilesOmitTheSyntaxDirective` следит за этим.

## Развёртывание из GitHub

1. Отправьте эту ветку (или смёрджите её) и подключите репозиторий на
   `dashboard.blitz.cloud` в разделе **Host something new → My own code**.
2. blitz.cloud находит корневой `Dockerfile` и compose-файл. Примите две части,
   которые он предлагает: `api` (публичная, на `/`) и `worker` (фоновая).
3. Создайте базу **PostgreSQL 17** на странице **Databases** и подключите её к
   приложению. blitz.cloud сам установит `DATABASE_URL`.

## Переменные окружения

Задайте их на вкладке **Environment** приложения. Значения с пометкой
*внедряется* предоставляет blitz.cloud, и задавать их вручную нельзя.

| Переменная | Значение | Примечания |
| --- | --- | --- |
| `FORGECRM_ENV` | `production` | Обязательна. |
| `DATABASE_URL` | *внедряется* | Строка подключения к управляемому PostgreSQL. Приложение читает сначала `FORGECRM_DATABASE_URL` и падает обратно на `DATABASE_URL`. |
| `FORGECRM_SECRET_KEY` | `openssl rand -base64 48` | Обязательна. Шифрует сохранённые учётные данные интеграций; её потеря делает их невосстановимыми. |
| `FORGECRM_BASE_URL` | `https://<app>.<you>.prod.page` | Обязательна. Используется для абсолютных ссылок. Берите адрес, по которому реально ходят пользователи: старый `<app>.<you>.blitz.cloud` отвечает `308` на `.prod.page` (см. «Адрес приложения» ниже). |
| `FORGECRM_MIGRATE_ON_START` | `true` | Задаётся на части **api**. По умолчанию флаг выключен; включите его, чтобы API применил миграции перед обслуживанием (иначе откажется стартовать и назовёт причину). |
| `FORGECRM_ROLE` | `worker` | Задаётся в `docker-compose.yml` на части **worker**. Выбирает бинарник входа образа (диспетчер `deploy/entrypoint.sh`), поэтому часть-воркер не поднимается как второй API. Задавать вручную не нужно. |
| `PORT` | *внедряется* | Его задаёт blitz.cloud; API слушает `0.0.0.0:$PORT`. |
| `FORGECRM_DATABASE_MAX_CONNS` | `6` (api), `4` (worker) | Память на бесплатном тарифе — 512 МБ; держите пулы небольшими. |
| `FORGECRM_RATE_LIMIT_STORE` | `memory` | Одна реплика, поэтому лимитер в процессе корректен. |
| `FORGECRM_VERSION` | `main` (или тег) | Необязательна. Метка версии. Сборка без build args штампует `dev`, а эта переменная её заменяет, поэтому укажите `main` (или тег), чтобы в `/ready` и в строке запуска была осмысленная версия. |
| `FORGECRM_COMMIT` | *(не задавайте)* | **Не задавайте её.** Корневой `Dockerfile` штампует SHA коммита из `.git` при сборке, поэтому `/ready` показывает именно собранный коммит. Ручное значение устаревает и перекрывает штамп — это и было причиной дефекта D-1 (см. `docs/audit/LIVE_PRODUCTION_BROWSER_QA.md`). Переменная остаётся только как запасной источник для локальной разработки, где `.git` внутри образа нет. |

### Метаданные сборки

`/ready` и строка запуска показывают версию и коммит. Источник — штамп сборки:
корневой `Dockerfile` читает `git rev-parse HEAD` из скопированного в образ
`.git` и передаёт результат в `-X main.commit`. blitz.cloud собирает корневой
`Dockerfile` сам и build args не передаёт, но `COPY . /meta` попадает в контекст
вместе с `.git`, поэтому коммит в `/ready` совпадает с развёрнутым кодом без
ручных переменных.

`FORGECRM_VERSION` и `FORGECRM_COMMIT` остаются запасным источником: бинарник
читает их только тогда, когда штамп пуст (например, локальная сборка без `.git`).
**Не задавайте `FORGECRM_COMMIT` на вкладке Environment.** Ручное значение не
обновляется вместе с кодом и перекрывает штамп, поэтому `/ready` начинает
показывать старый коммит, хотя развёрнут новый — именно это и было дефектом D-1.
Секретов эти переменные не содержат.

API слушает `PORT`, когда его задаёт blitz.cloud, иначе — `FORGECRM_HTTP_ADDR`
(по умолчанию `:8080`). Воркер ждёт схему, которую применяет API, прежде чем
начать забирать работу.

## Создание первого администратора

У API есть одноразовая команда bootstrap. На blitz.cloud откройте терминал части
**api** (или выполните одноразовую команду) и запустите:

```sh
FORGECRM_BOOTSTRAP_PASSWORD='choose-a-strong-password' \
  forgecrm-api -bootstrap-admin -bootstrap-email you@example.com
```

Пароль передаётся через окружение, поэтому он никогда не попадает в список
процессов. Затем войдите и создайте остальную команду со страниц администрирования.

## Поведение на бесплатном тарифе

Сверено с документацией blitz.cloud и проверено на живом приложении 6 ноября 2026.

- Часть **api** засыпает после 15 минут без **посетителей** и «масштабируется в
  ноль» — память она не держит. Будит её **визит человека в браузере**, а не
  запрос программы. Запросы программ (мониторы доступности, cron, скрипты,
  вебхуки, API-клиенты) приложение не будят: они получают `503`, и оно остаётся
  спящим. Первый визит ждёт пробуждения около 10 секунд.
- Часть **worker** работает в фоне и не спит, пока аккаунт активен. На бесплатном
  тарифе она останавливается, если в аккаунте ничего не происходит (нет входа,
  развёртывания или визита в панель) — **24 часа** для аккаунтов, открытых с
  5 ноября 2026, и 2 дня для открытых раньше; нажмите **Start** на странице
  приложения, чтобы возобновить. Ничего не теряется: задания, события outbox и
  запланированные workflow живут в PostgreSQL и продолжаются с места остановки.
- Одна управляемая база включена в бесплатный тариф и копируется каждую ночь.
  База **спит вместе с приложением**: она засыпает, когда все связанные с ней
  приложения спят или приостановлены, и поднимается раньше приложения при
  следующем пробуждении. Если база проспит целые сутки, диск аккаунта тоже
  «убирается», и первое пробуждение занимает на минуту-две больше. База без
  связанного приложения не спит.

### Сон и пробуждение: программа приложение не будит

Это ключевое отличие бесплатного тарифа blitz.cloud, и его легко принять за
сетевую неисправность. Спящее приложение отвечает на `/`, `/health` и `/ready`
одинаково:

```http
HTTP/2 503
content-type: application/json
cache-control: no-store
retry-after: 900
x-blitz-gate: asleep

{"status":"asleep",
 "message":"This app is asleep. A program cannot wake it. Opening it in a browser does. Pro keeps an app awake for a program too.",
 "upgradeUrl":"https://dashboard.blitz.cloud/settings?from=gate-wake#usage"}
```

- **`x-blitz-gate: asleep`** — ответ отдаёт шлюз blitz.cloud перед контейнером, а
  не сам ForgeCRM. Поэтому `/health` спящего приложения означает не «процесс
  жив», а «контейнер остановлен»; код приложения при этом не выполняется.
- **`retry-after: 900`** — 900 секунд = 15 минут, тот же срок, что и у сна.
- Ответ одинаков для `/`, `/health` и `/ready`: пока приложение спит, проверки
  живости и готовности ForgeCRM недостижимы.

**Программа приложение не будит.** Ни один инструмент API blitz.cloud (MCP-сервер
на `https://mcp.blitz.cloud/<account>`) спящую веб-часть не разбудит: вызова
«wake»/«start» нет, а `apps_resume` возобновляет только **приостановленное** или
**остановленное** приложение, не спящее. `files_download` и `files_upload_start`
работают «и спящим, и бодрым», но не будят его.

**Будит только визит человека в браузере.** Браузер открывает адрес, приложение
поднимается за ~10 секунд, и страница сама перезагружается, если пробуждение
затянулось (дольше 5 секунд показывается страница ожидания blitz.cloud).
Автоматизированный браузер (headless) или подмена `User-Agent` за человека не
считаются: в проверке 3 ноября 2026 ни то, ни другое приложение не разбудило.

**Чтобы программы доходили до приложения,** его надо «держать бодрым»
(`keepAwake`), и это платно:

- **Pro-приложение** — `keepAwake` на одном приложении, 2 EUR/мес (15 EUR/год). В
  MCP-API это поле `keepAwake` у `apps_update` («Never put to sleep for lack of
  visitors (Pro)»).
- **Pro-аккаунт** — 7 EUR/мес (70 EUR/год), до 50 приложений.

Поэтому мониторинг доступности бесплатное приложение бодрым не удерживает и не
будит: в документации blitz.cloud сказано прямо — «a check never keeps an app
awake», а запросы программ «get an answer that the app is asleep, and it stays
asleep». Монитор лишь получит `503` и сообщит о недоступности (хотя сам blitz.cloud
спящее приложение недоступным не считает).

Отдельно от сна по неактивности стоит остановка фонового воркера (см. выше): её
возобновляет **Start** в панели, а не браузерный визит к приложению.

### Адрес приложения

blitz.cloud отдаёт приложение и по `<app>.<account>.blitz.cloud`, и по
`<app>.<account>.prod.page`. Адрес `.blitz.cloud` отвечает `308` на `.prod.page`
(`x-blitz-gate: redirect`) — это тот же сервис. Для `FORGECRM_BASE_URL` берите
адрес, по которому реально ходят пользователи.

## Проверка развёртывания

```sh
base=https://<app>.<you>.prod.page
curl -fsSL "$base/health"   # -> {"service":"forgecrm","status":"ok","version":"main"}
curl -fsSL "$base/ready"    # -> {"status":"ready",...}
curl -fsSL -o /dev/null -w '%{http_code}\n' "$base/"   # -> 200 (веб-интерфейс)
```

`-L` обязателен: старый адрес `<app>.<you>.blitz.cloud` отвечает `308` на
`.prod.page`, и без `-L` `curl` вернёт пустое тело при коде `308`, а не JSON
(см. «Адрес приложения»).

`/health` — это живость (процесс поднят), `/ready` — готовность: база доступна,
схема применена **и её версия не отстаёт от версии запущенной сборки**. Если база
доступна, но миграции не применены, `/ready` отвечает `503` с причиной, а не `200`
— именно это раньше скрывало ошибку `relation "users" does not exist`. Тот же `503`
возвращается, когда таблицы есть, но применена не последняя миграция: обработчик,
добавленный новой миграцией, иначе отвечал бы `500` с той же ошибкой
`relation "..." does not exist`. База, ушедшая вперёд сборки, готовой считается:
применять миграции до выкатки нового кода — обычный порядок. Схема, помеченная
`dirty` (миграция упала на середине), тоже даёт `503`: таблицы при этом
существуют, и без проверки флага первый же запрос к добавленной колонке упал бы с
`column ... does not exist`. Worker миграции не запускает — он ждёт API, и ждёт
ограниченное время (`FORGECRM_WORKER_SCHEMA_WAIT`), после чего выходит с ошибкой,
а не висит. Неизвестный путь
`/api/...` остаётся JSON-ответом 404; любой другой путь отдаёт интерфейс, поэтому
клиентские маршруты переживают обновление страницы.

> **Спящее приложение даёт на эти команды `503`, а не `200`.** Ответ приходит от
> шлюза blitz.cloud (`x-blitz-gate: asleep`) и к живости или готовности ForgeCRM
> отношения не имеет — см. «Сон и пробуждение» выше. Прежде чем разбираться с
> `503`, откройте приложение в браузере и убедитесь, что оно проснулось.

Если прокси blitz.cloud добавляет `X-Forwarded-For`, задайте
`FORGECRM_TRUSTED_PROXIES` фактическими CIDR прокси, чтобы адрес клиента и его
лимит считались по настоящему источнику. Не используйте `*`.

## Проверка перед выкаткой

Развёртывание воспроизводится локально на чистой базе — тем же образом, той же
точкой входа и той же production-конфигурацией, что использует платформа:

```sh
docker build --build-arg VERSION=verify --build-arg COMMIT="$(git rev-parse --short HEAD)" \
  -t forgecrm-blitz-verify:latest .
make blitz-verify
```

`scripts/blitz-verify.sh` поднимает PostgreSQL 17, применяет миграции дважды,
создаёт первого администратора дважды, запускает API за TLS-прокси (production
требует `https` и `Secure`-cookie) и проходит весь путь: вход, `/me`, выход,
повторный вход, неверный пароль, отказ неаутентифицированной записи, и, наконец,
что `/health` остаётся `200`, а `/ready` становится `503`, когда схема удалена
из-под работающего процесса. Тот же прогон выполняется в CI (задание
`blitz-cloud`), поэтому сломанный образ или неприменённая миграция падают до
выкатки, а не на платформе.
