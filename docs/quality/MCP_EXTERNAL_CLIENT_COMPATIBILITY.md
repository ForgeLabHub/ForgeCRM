# Совместимость ForgeCRM MCP с внешним MCP-клиентом

Статус: проверено на реальном запущенном инстансе. Дата: 2026-11-05.

Это независимый отчёт по последнему незакрытому пункту проверки MCP: подключение
**настоящего внешнего MCP-клиента** к **реальному HTTP-инстансу** ForgeCRM и
выполнение MCP-вызовов через него. Он не повторяет уже доказанное (8 инструментов,
bearer-auth, RBAC, tenant isolation, `confirm`, аудит, отзыв) — он проверяет именно
совместимость клиента с сервером.

## 1. Клиент

| Параметр | Значение |
|---|---|
| Клиент | Официальный MCP Python SDK, пакет `mcp` |
| Версия SDK | **1.9.4** (сопутствующие: `pydantic` 2.11.7, `httpx` 0.28.1, `anyio` 4.16.0) |
| Transport | **Streamable HTTP** — `mcp.client.streamable_http.streamablehttp_client` |
| Authentication | HTTP-заголовок `Authorization: Bearer fcmcp_...` |
| Версия Python | 3.13 |

Установлен в изолированное окружение `/tmp/mcpverify/venv` **вне репозитория**.
Это стандартный клиентский транспорт SDK, а не написанный вручную JSON-RPC-код:
подключение, `initialize`, согласование версии, `tools/list` и `tools/call`
выполняет библиотека.

## 2. Окружение

| Компонент | Значение |
|---|---|
| API | собран из рабочего дерева (`go build ./cmd/forgecrm-api`), слушает `127.0.0.1:12000` |
| Endpoint | `POST /api/v1/mcp` (JSON-RPC 2.0) |
| База | одноразовая `forgecrm_mcp_e2e` в контейнере `forgecrm-it-pg` (PostgreSQL 17, порт 55432) |
| Redis | `forgecrm-it-redis` (Redis 7, порт 56379) |
| Организация | «Default organization» (`af3cae85-…`), отдельный пользователь-владелец |
| Второй тенант | «Isolated Org» — для проверки изоляции |
| Миграции | 33, применены чисто; схема version 33 |

Одноразовые контейнеры подняты штатным `scripts/integration-env.sh up` (файл не
изменялся). Секреты (secret key, пароль владельца, bearer-токены) сгенерированы
случайно, хранились только в `/tmp/mcpverify` с правами `600` и не попали ни в
репозиторий, ни в отчёт.

### Credential

Выдан через реальный API (`POST /api/v1/mcp/credentials`) с ровно запрошенной
минимальной областью:

```
ai.tools.execute, accounts.read, deals.read, tasks.read,
pipelines.read, reports.read, tasks.create, tickets.create,
deals.change_stage
```

Ни одного права сверх необходимого не добавлялось. Дополнительные права не
потребовались ни в одном сценарии.

## 3. Протокольные результаты

| Проверка | Результат |
|---|---|
| Соединение с `POST /api/v1/mcp` | ✅ установлено |
| `initialize` | ✅ успешно |
| Согласование protocol version | ✅ сервер ответил `2025-03-26` (запрошенный клиентом) |
| Server capabilities | ✅ `tools` (listChanged=false) |
| Server information | ✅ `forgecrm` v`1.0.0` |
| `tools/list` | ✅ **8 инструментов** |
| Input schemas | ✅ 8/8 содержат `properties` |
| `tools/call` (чтение) | ✅ 5/5 инструментов |
| `tools/call` (мутации) | ✅ 3/3 с `confirm:true` |
| Отказ авторизации | ✅ обработан как ошибка, не как успех |

Запрошенная клиентом версия `2025-03-26` — это значение по умолчанию в SDK 1.9.4.
Сервер поддерживает `2025-06-18`, `2025-03-26`, `2024-11-05` и корректно
эхо-возвращает выбранную. **Это не расхождение версий, а корректное согласование.**

### Наблюдение по transport (важно)

Сервер отвечает на POST **одиночным `application/json`-объектом JSON-RPC** и не
выдаёт заголовок `Mcp-Session-Id`. Это корректное **не-SSE подмножество** Streamable
HTTP: клиентский транспорт SDK принимает такой ответ. Клиент, который требовал бы
именно SSE-поток ответов или возобновляемость сессии, — отдельный вопрос; SDK 1.9.4
такого не требует. Замена Streamable HTTP обычным JSON-POST не производилась: вызовы
шли через `streamablehttp_client`.

## 4. Инструменты

Через внешний клиент вызваны:

**Read-only (5/5):**
- `search_accounts` — вернул список (1 результат);
- `list_tasks` — `{total, tasks}` (видимость ограничена RBAC: без `tasks.assign`
  видны только свои/командные задачи — это ожидаемое поведение, не дефект);
- `pipeline_overview` — данные по воронке;
- `get_report` (`sales_summary`) — отчёт;
- `account_summary` — разделы `account`, `deals`.

**Mutating (3/3, `confirm:true`), с проверкой в БД:**
- `create_task` → строка в `tasks` (status `open`);
- `create_ticket` → строка в `tickets` (status `new`);
- `update_deal_stage` → сделка «Acme Renewal» перешла в `status='won'`.

**Audit log** подтвердил всё: `ai.tool_invoked` (21 запись, `actor_type='ai_agent'`),
плюс доменные `tasks.create` ×2, `tickets.create` ×2, `deals.change_stage` ×2, и
`mcp.credentials.created`/`revoked`. Отказы тоже зафиксированы
(`pipeline_overview allowed=false`, `update_deal_stage allowed=false`).

## 6. Итог совместимости

**Внешний MCP-клиент совместим с реальным HTTP-инстансом ForgeCRM.**

- Внешний клиент: официальный MCP Python SDK 1.9.4, Streamable HTTP.
- Подключился, выполнил `initialize`, согласовал версию, получил capabilities и
  serverInfo.
- Обнаружил все 8 инструментов с корректными input schemas.
- Успешно выполнил read-only вызовы (5) и мутации (3) с `confirm:true`.
- Корректно обработал все отрицательные сценарии авторизации и прав.
- Несанкционированных изменений не произошло; секреты не утекли.
- Все тестовые credentials отозваны; тестовая инфраструктура удалена.

## 7. Ограничения

1. В окружении **не был предустановлен** отдельный MCP-клиент (официальный
   CLI/inspector или сторонний GUI). Использован официальный SDK с его клиентским
   транспортом — это допустимый вариант по условию проверки.
2. Проверено **не-SSE подмножество** Streamable HTTP. Поддержка SSE-стриминга
   ответов и возобновляемости сессии (`Mcp-Session-Id`) сервером не заявляется и не
   проверялась; клиент, который их требует, может быть ограничен.
3. `list_tasks` показал только задачи, назначенные вызывающему (RBAC record-level
   scoping). Это ожидаемое поведение; для видимости всех задач нужно `tasks.assign`.
4. Тесты совместимости жили вне репозитория (`/tmp/mcpverify`) и удалены после
   прогона; в репозитории остаётся только этот отчёт.
