# Тестовая архитектура (Phase 2)

> Phase 2 программы Quality & Reliability. Цель — сделать так, чтобы любой
> сценарий надёжности можно было проверить **воспроизводимо**: локально и в CI
> одинаково, без «проходит у меня». Этот документ описывает слои, изоляцию,
> фикстуры, моки и правила детерминизма. Он опирается на реестр из Phase 1
> ([FUNCTION_INVENTORY.md](FUNCTION_INVENTORY.md)).

## 1. Слои и что каждый доказывает

| Слой | Команда | Требует | Что доказывает |
| --- | --- | --- | --- |
| Unit | `go test -race ./...` | Go | бизнес-правила без БД; параллелизм в памяти |
| Architecture | `go test ./internal/archtest/` | Go | правила зависимостей и границы экстракции |
| Contract/OpenAPI | `make openapi-check` | Go | спецификация не разошлась с роутером |
| Integration | `make test-integration` | PostgreSQL (+Redis) | транзакции, RBAC, изоляция арендаторов, проводка HTTP |
| Benchmarks | `make test-bench` | черновая БД | записанная базовая линия, не гейт |
| E2E | `make test-e2e` | PostgreSQL + Chromium | пользовательские сценарии в браузере |

Слои не заменяют друг друга. Интеграционный тест не дублирует unit-тест: он
доказывает **проводку** — что обработчик подключён к запросу, что middleware
резолвит нужную организацию, что проверка прав выполняется до чтения.

## 2. Изоляция: у каждого тест-бинарника своя база

`internal/testdb` выводит из `FORGECRM_TEST_DATABASE_URL` приватную базу
`forgecrm_test_<пакет>_<pid>` и применяет к ней миграции один раз на бинарник.
Пакеты не делят схему, поэтому идут параллельно; раньше общая `public` заставляла
CI передавать `-p 1`.

`internal/testfixture.DB(t)` — надстройка: провизионит базу через `testdb` и
**сбрасывает** её (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;` + миграции),
чтобы тест стартовал с известного состояния. Сброс безопасен, потому что база
приватна бинарнику.

## 3. Фикстуры: `internal/testfixture`

Пакет убирает страницу SQL на тест и делает два факта явными: **какой арендатор**
и **какие права**. Он test-only; `internal/archtest` не даёт production-коду его
импортировать.

```go
db := testfixture.DB(t)                       // приватная база, чистая схема
org := testfixture.Tenant(t, db, "acme")      // организация + клонированные роли
owner := org.Owner()                          // principal с tenant_admin
viewer := org.Viewer()                        // principal только для чтения
g := testfixture.Connected(t, db, org)        // account+contact+pipeline+deal+task+ticket+activity
```

Что важно в устройстве:

- **Права резолвятся, а не выдумываются.** `Tenant` создаёт пользователя,
  членство и грант роли, затем вызывает `rbac.NewService(db).EffectivePermissions`,
  как это делает API. Principal из вручную заданного списка прав не проверял бы
  путь резолва — а именно там живёт привязка к арендатору.
- **Роли клонируются в организацию** (`ClonePlatformRoles`). Без этого грант не
  на что ссылать.
- **Slug уникален** (суффикс из случайного токена), поэтому два арендатора в одном
  тесте или остаток от прошлого прогона не сталкиваются по уникальному индексу.
- **Фабрики домена** (`Account`, `Contact`, `Lead`, `Pipeline`, `Deal`, `Task`,
  `Ticket`, `Activity`, `Connected`) заполняют только нужное, остальное —
  детерминированные умолчания.

Сам пакет проверяется интеграционными тестами (`fixture_test.go`): владелец
действительно получает права, viewer действительно уже, арендаторы действительно
изолированы, граф действительно связан. Фикстура без собственных тестов — это
фикстура, которая молча делает не то.

## 4. Моки: где реальное, где подставное

Правило из `docs/development/testing.md`: **unit-тесты не открывают БД**, а
интеграционные — **не подменяют БД моком**. Что подставляется и что нет:

| Компонент | Подход | Почему |
| --- | --- | --- |
| PostgreSQL | реальный сервер | свойства, которые проверяются (транзакции, ограничения, изоляция), мок удовлетворил бы по построению |
| Redis | реальный сервер | атомарный инкремент и общее окно между процессами — не то, что даёт фейк |
| Внешний HTTP (Telegram, webhook, SMTP) | подставной транспорт / `httptest` | третья сторона вне контроля; проверяется то, **что** отправлено и как обработан ответ |
| Сервисы домена | реальные | подмена домена проверяла бы подмену, а не домен |

`internal/testfixture.HTTPTransport` — скриптуемый `http.RoundTripper`: пишет
каждый запрос (метод, URL, заголовки, тело) и отдаёт заданный статус/тело. Он
потокобезопасен, потому что worker и API могут доставлять одновременно. Для
входящего HTTP используется `net/http/httptest` (сервер), а не заглушка клиента.

## 5. Детерминизм

- **Никаких `time.Sleep` как синхронизации.** Ожидание — через каналы и
  `context`; таймаут в тесте — только как страховка от зависания, не как мера.
- **Никакой зависимости от порядка.** Каждый тест сам создаёт свои данные с
  уникальными id; `go test` по умолчанию перемешивает порядок внутри пакета, и
  тест, зависящий от предыдущего, падает — это и есть цель.
- **Время.** У планировщика есть шов `httpx.RateLimitOptions.Now` для лимитера;
  для остального время берётся из `time.Now` и тесты не закладываются на
  конкретные даты.
- **Отсутствие сервера = skip, а не fail.** Без `FORGECRM_TEST_DATABASE_URL`
  интеграционные тесты пропускаются, поэтому `go test ./...` остаётся зелёным на
  машине без PostgreSQL.

## 6. Локальный прогон = CI

Ключевой риск Phase 2: тест, который проходит локально и не доказывает
надёжность в CI. Две меры против него:

1. **Одинаковые образы и порты.** `scripts/integration-env.sh up` поднимает
   `postgres:17-alpine` и `redis:7-alpine` — те же, что сервисы джобы `backend`
   в `.github/workflows/ci.yml`. Порты локально иные (55432/56379), чтобы не
   конфликтовать с рабочим стеком, но версии совпадают.
2. **Одинаковая команда.** И там, и там — `go test -count=1 -tags=integration ./...`
   с `FORGECRM_TEST_DATABASE_URL` и `FORGECRM_TEST_REDIS_URL`. Пакеты идут
   параллельно без `-p 1` (см. §2).
3. **Гейт против «зелёного прогона, который ничего не выполнил».** Тесты без
   `FORGECRM_TEST_DATABASE_URL` пропускаются — это верно для локального
   `go test ./...`, но в CI с `-tags=integration` означало бы, что прогон
   отчитался об успехе, не выполнив ни одного интеграционного теста. Поэтому
   `internal/testdb` содержит канарейку `TestIntegrationEnvironmentIsConfigured`:
   она **не** пропускается и падает, если `FORGECRM_TEST_DATABASE_URL` или
   `FORGECRM_TEST_REDIS_URL` не заданы. Имена переменных объявлены один раз
   (`testdb.URLEnv`, `testdb.RedisURLEnv`) и используются тестами и канарейкой,
   чтобы литерал не разошёлся с тем, что читают тесты.

```bash
./scripts/integration-env.sh up
export FORGECRM_TEST_DATABASE_URL='postgres://forgecrm:forgecrm@127.0.0.1:55432/forgecrm_test?sslmode=disable'
export FORGECRM_TEST_REDIS_URL='redis://127.0.0.1:56379/1'
make test-integration TEST_DATABASE_URL="$FORGECRM_TEST_DATABASE_URL"
./scripts/integration-env.sh down
```

Зафиксированный результат этого прогона: **ok 45 / FAIL 0** (было 44 до
добавления `internal/testfixture`).

## 7. Известные пробелы (вход в следующие фазы)

- **Worker как отдельный процесс**: закрыт в Phase 8 — `cmd/forgecrm-worker`
  собирается и запускается как реальный процесс в deploy-подобном окружении
  (`runtime_integration_test.go`), см. §9.
- **Нагрузочных тестов нет** (только однопоточная базовая линия `make test-bench`).
- **Fault injection** (БД/Redis недоступны, пул исчерпан) не автоматизирован.
- **Property-based тестов домена** нет, кроме точечных случаев.

## 8. Изменения Phase 2

- `backend/internal/testfixture/` — новый test-only пакет: тенанты, доменные
  фикстуры, подставной HTTP-транспорт, собственные тесты.
- `scripts/integration-env.sh` — одноразовое окружение PostgreSQL+Redis,
  совпадающее с CI по образам.
- `backend/internal/archtest/arch_test.go` — `testfixture` внесён в список

  допускает импорт test-only из test-only.
- `docs/development/testing.md` — упомянуты фикстуры и локальное окружение.

## 9. Runtime-надёжность worker (Phase 8)

Отдельный файл `cmd/forgecrm-worker/runtime_integration_test.go` доказывает то,
чего не видит тест отдельной функции: собранный бинарник действительно стартует,
подключается, забирает job из БД, выполняет его и корректно завершается по
сигналу. Тесты запускают **настоящий процесс** (`go build` + `exec`), а не
вызывают `workerLoop` напрямую.

- `TestWorkerBinaryExecutesAJobFromTheDatabase` — enqueue через реальную очередь,
  ожидание терминального статуса, проверка **наблюдаемого побочного эффекта**
  (устаревший каталог импорта удалён), heartbeat в `worker_heartbeats`, затем
  SIGTERM: процесс перестаёт забирать работу и выходит с кодом 0.
- `TestWorkerBinaryRecoversAJobFromACrashedWorker` — job оставлен в `running` с
  просроченным lock (состояние после падения воркера); второй процесс поднимается
  и завершает его. Requeue-петля теперь восстанавливает такие job **на старте**, а
  не только по тику (см. §10).
- `TestWorkerBinaryDrainsOutboxIntoDeliveries` — доменное событие эмитится в
  outbox, реальный воркер его публикует и создаёт webhook-доставку. Это путь,
  который раньше молча ничего не делал: события записывались, потребителя не было.

Ограничение, зафиксированное явно: реальный воркер доставляет webhook через
production-SSRF-guard, который корректно отвергает loopback. Поэтому сквозная
доставка на локальный sink проверяется в процессных тестах с подставным
транспортом (§4), а не через настоящий бинарник; бинарник проверяет, что событие
дошло до таблицы доставок с нужной формой.

## 10. Прочие изменения Phase 8

- `internal/testsupport/queue_integration_test.go` — семантика очереди на реальном
  PostgreSQL: эксклюзивность claim между воркерами (`FOR UPDATE SKIP LOCKED`),
  пропуск будущих и отменённых job, ретрай с backoff и исчерпание попыток,
  возврат просроченных job. Тест живёт в `testsupport`, а не в `internal/jobs`:
  ему нужны `migrate` и `testdb`, которые извлечённый модуль `jobs` импортировать
  не должен — иначе `scripts/extract-test` перестанет его извлекать.
- `runRequeueLoop` восстанавливает просроченные job один раз при старте, как это
  уже делали outbox- и delivery-петли. Раньше рестарт после падения оставлял
  «зависшие» job ещё на полный тик (2 минуты).
- `internal/jobs/handler_coverage_test.go` — `TestEveryDeclaredKindIsDispatchedOrReserved`
  читает `jobs.go` и `cmd/forgecrm-worker/main.go` через `go/parser` и требует,
  чтобы каждый объявленный `Kind*` либо имел `case` в диспетчере воркера, либо
  был явно перечислен в `reservedKinds`. Так новый kind не может появиться и
  молча никогда не выполняться. Диспетчер живёт в бинарнике, а не в пакете, поэтому
  в извлечённом модуле `jobs` (где `cmd/` отсутствует) тест пропускается: там
  проверяется независимость, а не покрытие диспетчера.

## 11. MCP: сквозной сценарий агента

`internal/api/mcp_scenario_integration_test.go` проходит весь путь, которым
пользуется автономный агент, на реальном роутере, middleware прав и базе:

- подключение **bearer-credential** (у агента нет сессии — это единственный
  способ подключиться), обнаружение всех восьми инструментов;
- чтение `account_summary` и проверка границы прав: инструмент отдаёт
  `recent_activity`, но **не** `deals` и `tickets`, если у credential нет
  `deals.read`/`tickets.read`;
- `create_task`, `create_ticket`, `update_deal_stage` — каждый с `confirm:true`,
  с проверкой фактической записи в БД;
- **аудит**: каждый вызов оставляет `ai.tool_invoked` с `actor_type='ai_agent'`,
  а каждая мутация — доменную запись (`tasks.create`, `tickets.create`,
  `deals.change_stage`);
- **отзыв** credential закрывает доступ (401).

Положительный контроль `TestMCPAccountSummaryIncludesSectionsWhenPermitted`
проверяет обратную сторону границы: с выданными правами разделы `deals`,
`tickets`, `recent_activity` обязаны присутствовать. Без него баг, который
безусловно вырезал бы эти разделы, прошёл бы «проверку на утечку». Граница
проверена мутационно: снятие `if p.Has(rbac.PermDealsRead)` валит сценарий.

Что этот слой **не** доказывает: что произвольный внешний MCP-клиент подключится
к развёрнутому инстансу. Bearer-credential в тесте проходит через тот же
HTTP-путь, что и внешний клиент, но само подключение клиента — задача интеграции
клиента, а не свойство сервера.
