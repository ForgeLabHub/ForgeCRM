Словарь статусов, используемый во всей документации:

| Статус | Значит |
|---|---|
| **Implemented** | Код существует, компилируется и достижим из работающего процесса. |
| **Tested** | Покрыт проходящими автоматическими тестами, включая негативные случаи. |
| **Verified** | Протестирован **и** упражнён против реальной зависимости (база, браузер, провайдер) с записанной командой и результатом. |
| **Partial** | Часть описанного поведения существует; пробел указан. |
| **Planned** | Спроектировано, не построено. |
| **Blocked** | Нельзя продолжить без чего-то вне нашего контроля. Блокер назван. |
| **Deprecated** | Заменено; сохранено только для миграции. |

Функция никогда не описывается как Verified потому, что пакет, страница или флаг
конфигурации носят её имя. Верификация требует записанного доказательства.

## 1. Определение продукта

ForgeCRM — это самостоятельно размещаемая CRM-платформа с открытым исходным кодом и
модульной архитектурой, созданная для:

- продаж и управления клиентами;
- поддержки клиентов;
- корпоративных бизнес-процессов;
- миграции из существующих CRM-систем;
- подключения к корпоративным базам данных;
- интеграции с ERP и внешними API;
- автоматизации на событиях и правилах;
- ИИ-помощи и MCP;
- быстрой адаптации к неизвестным сценариям хакатонов.

**Ключевой принцип:** одна устойчивая основа, много адаптируемых бизнес-решений.

**Жёсткое требование:** продукт работает сам по себе, без ИИ, без внешних API и без
опциональных интеграций. Каждая интеграция переключаема и настраиваема.

### Четыре направления

| Направление | Область |
|---|---|
| **Universal CRM** | Контакты, аккаунты, лиды, сделки, задачи, активности, обращения, профили клиентов. |
| **Adaptive Platform** | Конфигурация тенанта, кастомные объекты, поля, роли, воронки, модули. |
| **AI Intelligence** | MCP, копилот, автономные агенты, извлечение, объяснимые рекомендации. |
| **Automation & Integrations** | Workflow, события, вебхуки, SDK, внешние системы. |

Все четыре используют одну модель безопасности, один журнал аудита и один набор
доменных правил. Это ограничение, а не стремление: именно поэтому архитектура —
модульный монолит (ADR 0001) и поэтому выделение требует измеренного триггера
(ADR 0002).

## 2. Принципы архитектуры

1. **Сначала модульный монолит.** Ясные границы модулей; независимые сервисы только
   когда достигнут и записан триггер из ADR 0002.
2. **Одна реализация каждого правила.** API, MCP, воркер и будущий SDK вызывают одни
   и те же доменные операции и одни и те же политики доступа.
3. **Нет циклов импорта.** Обеспечено тестами в `backend/internal/archtest`.
4. **Явные границы транзакций.** Доменная операция либо коммитится, либо нет.
5. **Идемпотентность для повторяемых операций.** Задания, импорты и события
   спроектированы для повторов, а не в предположении одного запуска.
6. **Версионированные API и события.** Ломающее изменение контракта требует версии и
   пути миграции.
7. **PostgreSQL — источник истины.** Ничто другое не становится вторым источником.
8. **Опциональные компоненты остаются опциональными.** Redis, брокер сообщений и
   объектное хранилище вводятся для названной потребности, никогда как базовая
   зависимость.
9. **Падать видимо.** Неверная конфигурация — это ошибка старта, называющая
   исправление, а не молчаливое ограничение, всплывающее позже как необъяснимые
   тайм-ауты.
10. **Безопасность — на сервере.** Скрытие элемента UI — не авторизация.

## 3. Модель безопасности

Непреложные инварианты. Конфигурация тенанта никогда не может их отключить:

| Инвариант | Обеспечение |
|---|---|
| Каждый запрос аутентифицирован | middleware `requireSession`, единственное место установления личности |
| Каждое решение авторизации на сервере | `rbac.Principal` определяется из сессии; обработчики проверяют права, а не UI |
| Изоляция тенантов в каждом запросе | Область организации в запросе, а не пост-фильтр |
| Аудит привилегированных и значимых для безопасности действий | Пакет `audit` «только добавление» |
| Никаких секретов в логах, ответах или репозитории | Сокрытие в `logging`; сканирование секретов в CI |
| Никакого сырого SQL, shell или доступа к файловой системе через ИИ или MCP | Белый список инструментов с проверкой прав на инструмент |

Модель угроз, границы доверия и безопасность ИИ детально описаны в
`docs/SECURITY.md` и `docs/AI_SAFETY.md`.

## 4. Фазы и определение готовности

Фазы — это порядок приоритетов, а не запрет параллельной работы. Каждая фаза
завершается опубликованным, проверенным инкрементом.

| Фаза | Область | Критерий выхода |
|---|---|---|
| **0. Безопасный старт** | Аудит, мастер-документы, ADR, критические блокеры | Документы описывают проверенную реальность; блокеры названы |
| **1. Контракты и база платформы** | OpenAPI 3.1, контракт RFC 9457, контрактные тесты, справочник API, распределённое ограничение частоты, размер пула, диагностика | Контракт API машинно-проверяем, и CI падает, когда код и контракт расходятся |
| **2. Идентичность и безопасность** | OIDC Authorization Code + PKCE, тестовый IdP, проверки RBAC и тенанта, управление согласием | Реальный поток IdP проходит интеграционные тесты; согласие обеспечивается в каждом канале |
| **3. MCP и ИИ-нативный UX** | Сервер протокола MCP, инструменты чтения и безопасной записи, UI MCP, контекстный ИИ, калиброванная уверенность, корректный сбой, передача человеку | Внешний MCP-клиент подключается и правильно отклоняется без разрешения |
| **4. Агентная система** | Runtime агента, бюджеты, область, observe/suggest/act-with-approval, три начальных агента | Нарушения бюджета и области отклоняются и аудируются |
| **5. Адаптация тенанта** | Конфигурация тенанта, bootstrap, кастомные объекты, SDK, CLI | Кастомный объект работает от начала до конца через API, UI и RBAC |
| **6. Данные клиентов и сотрудничество** | Разрешение идентичности, золотая запись, UI слияния, обновления в реальном времени | Слияние транзакционно, аудируется и безопасно для тенанта |
| **7. Мобильность и аналитика** | Адаптивный UI, PWA, офлайн-чтение, офлайн-очередь записи, встроенная аналитика | Создание задачи офлайн синхронизируется с обнаружением конфликтов |
| **8. Автоматизация и инфраструктура** | Конструктор workflow, подписки на события, отладчик вебхуков, объектное хранилище, проверка резервных копий, панель эксплуатации | Восстановление проверено на чистой изолированной базе |
| **9. Полировка и документация** | Дизайн-система, единый UI, доступность, анимации, README, сайт документации | Новый разработчик запускает проект по документам на чистой машине |

### Определение готовности

Задача завершена только когда отмечены все применимые пункты:

- [ ] Реальная реализация завершена
- [ ] Код отформатирован (`gofmt`, Prettier)
- [ ] Бэкенд компилируется, `go vet` чист
- [ ] Линт фронтенда и проверка типов TypeScript чисты
- [ ] Модульные тесты проходят
- [ ] Интеграционный тест для успешного пути
- [ ] Негативные тесты
- [ ] Проверена изоляция тенантов
- [ ] Проверены права
- [ ] Проверены пути ошибки, тайм-аута и отмены, где применимо
- [ ] Добавлен E2E для критических пользовательских сценариев
- [ ] OpenAPI обновлён при изменении API
- [ ] Документация обновлена
- [ ] Дорожная карта обновлена
- [ ] Миграции проверены на чистой **и** обновлённой базе
- [ ] Нет новых секретов, небезопасных заглушек или лишних файлов
- [ ] CI проверен против конкретного SHA коммита
- [ ] Изменения опубликованы в разрешённой ветке
- [ ] Сообщение о завершении соответствует реальному результату

Если проверку нельзя запустить из-за внешней зависимости, указывается точная причина,
и проверка не сообщается как пройденная.

## 5. Правила поставки

Это ограничения на то, как выполняется работа, а не предпочтения:

1. Никаких пустых эндпоинтов.
2. Никаких кнопок без работающего действия.
3. Никаких заглушек вместо обещанной логики.
4. Никакого мока вместо реальной интеграции в production.
5. Тесты никогда не меняются, чтобы сделать результат зелёным.
6. Проверки безопасности никогда не отключаются, чтобы пройти CI.
7. Падающие тесты никогда не скрываются.
8. Никакой зависимости без заявленной причины.
9. Никаких несвязанных рефакторингов.
10. Никакого изменения контракта API без проверки совместимости.
11. Никакой разрушительной миграции без плана миграции данных.
12. Никакого удаления данных, файлов или веток без проверки последствий.
13. Облачный сервис никогда не сообщается как работающий, пока не проверено реальное
    соединение.
14. SSO никогда не сообщается как готовое на основании одной лишь конфигурации.
15. Модульный монолит никогда не описывается как микросервисы.
16. Никаких заявлений о соответствии GDPR или иному без достаточных оснований.
17. Никаких секретов в Git, логах, документации или скриншотах.
18. Никаких платных запросов ИИ без доступного бюджета и явного разрешения.
19. Никаких реальных писем, сообщений Telegram или вызовов вебхуков в тестировании
    без изолированного окружения.
20. Никаких необратимых действий в production.
21. Никаких выдуманных метрик производительности, результатов тестов или статуса
    публикации.
22. Фаза не начинается, пока критические проверки предыдущей фазы падают.
