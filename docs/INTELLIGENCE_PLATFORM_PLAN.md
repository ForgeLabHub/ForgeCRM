# ForgeCRM Intelligence Platform — архитектура и план поставки

Этот документ — архитектурный план слоя интеллекта, который сидит поверх
существующего ForgeCRM. Он фиксирует, что уже существует, что строит эта итерация,
что намеренно отложено, и критерии, решающие, когда каждая часть готова. Он написан
против реального репозитория, а не предполагаемого.

План — рабочий документ. Когда раздел закончен, это помечается, а строка статуса
называет коммит или тест, который это доказывает.

---

## 1. Текущее состояние проекта

ForgeCRM — самостоятельно размещаемая CRM-модульный монолит: бэкенд на Go (модуль
`github.com/geff1778/forgecrm`), PostgreSQL, фронтенд React + TypeScript + Vite,
обслуживаемый в том же источнике через Nginx. Два бинарника делят один граф объектов,
построенный в `internal/wiring`: `forgecrm-api` и `forgecrm-worker`.

Подсистемы, которые уже существуют и переиспользуются этим планом, проверенные в коде:

| Подсистема | Пакет | Что даёт слою интеллекта |
|---|---|---|
| Ядро CRM | `internal/crm` | Сущности, правила, чтения с проверкой прав. `SalesSummary`, `SupportSummary`, `PipelineReportFor` уже существуют. |
| RBAC | `internal/rbac` | Каталог разрешений (`rbac.All()`), `Principal`, `s.perm(...)` на маршрут. |
| Аудит | `internal/audit` | `audit_log` + `security_events` «только добавление»; `Record` использует окружающую транзакцию. |
| База данных | `internal/database` | `DB.Q(ctx)` (осведомлённый о транзакции), `WithTx`, `Querier`. |
| Задания | `internal/jobs` | Долговечная очередь с `EnqueuePeriodic`, дедупликацией по advisory-блокировке, повторами. |
| Слой ИИ | `internal/ai` | Абстракция провайдера (`Provider`, `Complete`), сборка контекста с проверкой прав (`Assist`). |
| Outbox / события | `internal/outbox`, `internal/events` | Словарь событий `outbox.EventTypes()`, диспетчер. |
| Движок workflow | `internal/workflow` | Валидация определения, map шаг→разрешение, история прогонов. |
| Хранилище | `internal/storage` | Вложения, совместимые с S3. |
| OpenAPI | `internal/api/contract.go`, `internal/openapi` | Сгенерированная спецификация из живого роутера; гейт `-check` в CI. |
| Правила архитектуры | `internal/archtest` | Обеспечивает стрелки зависимостей. |

### 1.1 Существующие возможности аналитики (не дублировать)

- `crm.SalesSummary(ctx, p, from, to)` — сделки созданные/выигранные/проигранные,
  стоимость выигранных/проигранных/открытых, средняя сделка, доля выигрышей.
- `crm.SupportSummary(ctx, p)` — всего обращений, открытые/решённые, нарушения SLA,
  среднее время решения, счётчики по приоритету.
- `crm.PipelineReportFor(ctx, p, pipelineID)` — по стадиям число сделок, общая и
  взвешенная по вероятности сумма, суммы выигранных/проигранных.

Это **базовые читатели**. Ядро аналитики их потребляет; оно их не переписывает.

### 1.2 Дефекты, найденные при аудите

1. **Страница Reports читает поля, которые API не возвращает.** Бэкенд возвращает
   `deals_won`, `won_value`, `open_value`, `win_rate`, `total`, `resolved`,
   `avg_resolution_hours` (подтверждено в `docs/api/openapi.json`). Типы фронтенда в
   `src/types/api.ts` объявляют `won_count`, `won_amount`, `opened`,
   `avg_resolution_minutes`. Поэтому страница отрисовывает `undefined` для каждой
   ключевой цифры. Исправлено в этой итерации (§5.4).
2. **Деньги несутся как `float64`.** `deals.amount` — это `numeric(18,2)` (точно), но
   структуры отчётов сканируют в `float64`. Задача запрещает `float64` для денег. Ядро
   аналитики вводит точный тип `analytics.Money`; существующие структуры отчётов
   оставлены как есть для совместимости API, но не используются для арифметики
   симуляции.

### 1.3 Частично реализованное / честные пробелы

- Слой ИИ провайдеро-агностичен, но **нет** общего помощника «выполнить структурный
  вызов модели и разобрать типизированный результат»; контекстный путь — это текст на
  входе / текст на выходе. Этой итерации он не нужен, поэтому не строится.
- Нет прогнозирования, нет оценки риска, нет оценки качества данных, нет конвейера
  извлечения документов. Это пункты дорожной карты (§9).

## 2. Целевая архитектура

```
                    ┌───────────────────────────────────────────────┐
   HTTP /api/v1     │  internal/api  (слой композиции)               │
                    │   - регистрация маршрутов + разрешение на маршрут │
                    │   - таблица контракта → OpenAPI                │
                    └───────────────┬───────────────────────────────┘
                                    │ зависит от
              ┌─────────────────────┼───────────────────────┐
              ▼                     ▼                       ▼
    ┌──────────────────┐  ┌──────────────────┐  ┌────────────────────┐
    │ internal/simulate│  │ internal/crm      │  │ internal/ai        │
    │  Scenario Lab    │  │  базовые читатели │  │  слой провайдера   │
    │  сервис          │  │  (воронка, сделки)│  │                    │
    └────────┬─────────┘  └──────────────────┘  └────────────────────┘
             │ использует
             ▼
    ┌──────────────────────────────────────┐
    │ internal/analytics  (чистое ядро)     │
    │  - Money (точные, целые центы)        │
    │  - детерминированная математика сценариев │
    │  - без БД, без HTTP, без часов, без ИИ │
    └──────────────────────────────────────┘
```

### 2.1 Ответственность модулей и границы

- **`internal/analytics`** — чистое ядро. Точная арифметика денег, математика воронки и
  выручки, валидация параметров и контракты результатов. Импортирует **только**
  стандартную библиотеку. Ни базы, ни HTTP, ни ИИ, ни `time.Now()`. Всё здесь
  детерминировано и покрываемо юнит-тестами без инфраструктуры. Это граница, которая
  делает математику проверяемой и воспроизводимой.
- **`internal/simulate`** — прикладной сервис. Он читает базовую линию из CRM через
  `crm.Service` с принципалом вызывающего (поэтому изоляцию тенантов и права на объекты
  обеспечивает читатель, а не пере-реализация), вызывает чистое ядро, сохраняет прогоны
  и сценарии и пишет записи аудита. Он зависит от `crm`, `analytics`, `audit`,
  `database`, `rbac`, `httpx`. Ядро его не импортирует.
- **`internal/api`** — маршруты, DTO запроса/ответа, строки контракта.
- **фронтенд** — страница Simulation Lab в существующей дизайн-системе.

Это соблюдает существующие правила архитектуры: `analytics` — лист, как `crm`;
`simulate` — прикладной сервис, который может зависеть от ядра.

### 2.2 Почему новый пакет, а не «ещё методы на crm.Service»

Математика должна быть тестируема без базы, не должна трогать часы и не должна уметь
читать данные самостоятельно. У `crm.Service` есть дескриптор базы и он читает строки;
помещение чистой арифметики туда сделало бы арифметику зависимой от схемы и позволило
бы сценарию случайно записать. Отдельный пакет-лист с односторонней зависимостью держит
арифметику проверяемой и держит свойство «симуляция никогда не пишет» структурным, а не
соглашением.

## 3. Модель данных и миграции

Новые таблицы (миграция `0019_simulation_lab`), все с областью тенанта:

- `simulation_scenarios` — сохранённый сценарий: организация, владелец, имя, `kind`
  сценария, набор параметров как `jsonb`, версия алгоритма, временные метки,
  `archived_at` для мягкого удаления. Уникально `(organization_id, name)` среди живых
  строк.
- `simulation_runs` — одно исполнение сценария: организация, id сценария,
  **замороженный** набор параметров и снимок базовой линии (`jsonb`), версия алгоритма,
  точный результат (`jsonb`), кем создан, `created_at`. Неизменяемо.

Деньги хранятся в результатах `jsonb` как **целые минорные единицы** (`amount_minor` +
`currency`) плюс строка отображения, никогда как float, поэтому сохранённый результат
точен и перезагрузка не может его сдвинуть.

Индексы: `simulation_scenarios (organization_id, owner_user_id)`,
`simulation_runs (organization_id, scenario_id, created_at DESC)`.

Миграции `up`/`down` добавляются пронумерованной парой. Ни одна существующая миграция
не правится.

Разрешения (то же изменение, что и каталог Go): `simulation.read`, `simulation.manage`,
`simulation.run`, засеянные в роли вставкой в стиле `seed_grant`, повторяя миграции
0006/0010/0013.

## 4. План API

Всё под существующей аутентифицированной группой; каждый маршрут объявляет разрешение.

| Метод | Путь | Разрешение | Назначение |
|---|---|---|---|
| GET | `/api/v1/simulation/scenarios` | `simulation.read` | Список каталога + сохранённых сценариев организации |
| POST | `/api/v1/simulation/scenarios` | `simulation.manage` | Сохранить сценарий |
| GET | `/api/v1/simulation/scenarios/{id}` | `simulation.read` | Открыть сохранённый сценарий |
| DELETE | `/api/v1/simulation/scenarios/{id}` | `simulation.manage` | Архивировать сценарий |
| POST | `/api/v1/simulation/scenarios/{id}/runs` | `simulation.run` | Запустить сохранённый сценарий, сохранить результат |
| GET | `/api/v1/simulation/scenarios/{id}/runs` | `simulation.read` | История прогонов сценария |
| POST | `/api/v1/simulation/preview` | `simulation.run` | Запустить несохранённый набор параметров (без сохранения) |

Каждое тело запроса и ответ названы в `internal/api/contract.go`, а документ OpenAPI
перегенерируется через `go run ./cmd/openapi-gen`.

## 5. Simulation Lab — вертикальный срез

### 5.1 Сценарии (три, все реальные)

**Funnel** (`funnel`). Входы: множитель конверсии по стадиям или явное переопределение
конверсии и опциональный множитель объёма лидов. База: живые счётчики сделок по стадиям
воронки и суммы сделок. Выход: ожидаемое число закрытых сделок и ожидаемая выигранная
стоимость для базы и варианта, плюс дельта. Математика — постадийный проход по ожидаемой
стоимости; это **детерминированный расчёт на заявленных допущениях**, никогда не
называемый статистическим прогнозом.

**Revenue** (`revenue`). Входы: множитель среднего чека, множитель доли выигрышей,
множитель числа сделок. Выход: ожидаемая выручка для базы и варианта и относительное
изменение. Использует точные деньги.

**Retention** (`retention`). Входы: предполагаемая доля оттока (параметр, который
задаёт пользователь, с умолчанием и явным диапазоном) и база удерживаемой стоимости.
Результат — **параметрическая** оценка при заявленных допущениях. UI и документы
помечают её как параметризованную модель, а не обученный прогноз. Если у организации нет
истории закрытых/выигранных, прогон сообщает «недостаточно данных» вместо числа.

### 5.2 Свойства корректности (тестируются)

- Симуляция никогда не пишет строки CRM. У сервиса нет пути записи в CRM; читатель
  только для чтения. Интеграционный тест утверждает, что счётчики сделок/задач/
  активностей не изменились за прогон.
- Симуляция никогда не запускает workflow, вебхуки, уведомления или письма.
- Детерминизм: идентичный вход + параметры + версия алгоритма ⇒ идентичный результат.
  Юнит-тест прогоняет ядро дважды и сравнивает.
- Нулевые знаменатели, отрицательные входы, параметры вне диапазона и пустые выборки
  дают явные ошибки валидации, а не NaN/Inf.
- Размер выборки, диапазоны параметров и лимиты строк на прогон ограничены.

### 5.3 Воспроизводимость и версионирование

Каждый результат записывает `algorithm_version`. Ядро выставляет свою версию как
константу; прогон её сохраняет. `params` и `baseline` сохранённого прогона заморожены,
поэтому повторный прогон после изменения кода сопоставим: разница объяснима версией.

### 5.4 Интерфейс

Новый пункт **Simulation Lab** в навигации Workspace, использующий существующие
компоненты `ui.tsx` (PageHeader, Card, Stat, Field, Alert, ErrorState, ConfirmDialog).
Состояния: загрузка, пусто, ошибка, «провайдер не нужен» и ошибки валидации. Страница
показывает формулу и допущения для выбранного сценария и историю сохранённых прогонов с
возможностью повторного открытия и повторного запуска.

Несоответствие контракта страницы Reports (§1.2) исправляется здесь:
`src/types/api.ts` исправлен на реальные имена полей, а `ReportsPage.tsx` обновлён в
соответствии.

## 6. Риски безопасности и производительности

- **Изоляция тенантов.** Каждое чтение идёт через `crm.Service` с принципалом
  вызывающего; каждая запись фильтрует `organization_id`. Тестируется случаем с двумя
  организациями.
- **Авторизация объектов.** Сохранённый сценарий читаем/удаляем только внутри своей
  организации; id из другой организации возвращает «не найдено».
- **Никаких секретов никакой модели.** Этот срез вообще не вызывает модель. Когда
  ИИ-помощь будет наложена позже, она использует существующий путь `ai.Service`,
  который маскирует персональные данные.
- **Ограничения ресурсов.** Тела запросов ограничены по размеру существующим
  декодером; диапазоны параметров и число строк результата ограничены в ядре; запрос
  ограничен периодом вызывающего и организацией.
- **Производительность.** Никаких заявлений о нагрузочном тестировании не делается.
  Читатель базовой линии — агрегатный SQL по индексированным столбцам; результат
  вычисляется в памяти из ограниченных агрегатов.

## 7. Последовательность реализации

1. `internal/analytics` (чистое ядро) + юнит-тесты. *(готово — §status)*
2. Читатель базовой линии в `crm` для входов воронки/выручки.
3. Сервис `internal/simulate` + сохранение.
4. Миграция 0019 + сид разрешений; каталог Go.
5. Маршруты API + DTO + контракт + перегенерация OpenAPI.
6. Страница фронтенда + типы + навигация.
7. Исправление страницы Reports.
8. Интеграционные тесты (PG), тесты фронтенда, E2E.
9. Документация.

## 8. Определение готовности для этой итерации

1. Три работающих сценария с реальными или ясно помеченными данными.
2. Сохранение и повторное открытие работают; результаты сохранены точно и
   воспроизводимы.
3. Симуляция доказуемо не изменяет данные CRM (интеграционный тест).
4. Юнит-тесты алгоритма с известными ожидаемыми значениями; граничные тесты.
5. Интеграционные тесты бэкенда на PostgreSQL; E2E для create→run→save→re-open.
6. Никакой регрессии CRM: существующие наборы остаются зелёными.
7. Документы и дорожная карта соответствуют коду.
8. `gofmt`, `go vet`, `go test`, OpenAPI `-check`, typecheck/lint/build фронтенда.

## 10. Статус

- **Аудит §1** — готово, этот документ.
- **§2–§5 ядро аналитики + Simulation Lab** — готово. Чистое ядро
  (`internal/analytics`, точные деньги и доли, `simulate-v1`) вышло первым; затем
  читатель базовой линии `crm`, сервис `internal/simulate`, миграция
  `0019_simulation_lab` с тремя сидами разрешений, поверхность API (CRUD сценариев,
  прогон, предпросмотр, каталог только для сессии) и перегенерация OpenAPI. Фронтенд —
  это пункт `Simulation Lab` в навигации Workspace
  (`frontend/src/pages/SimulationPage.tsx`, `frontend/src/api/simulation.ts`).
- **Тесты** — `internal/testsupport/simulation_test.go` (PostgreSQL) покрывает CRUD
  сценариев и архивирование, уникальное имя по организации, валидацию параметров при
  сохранении, изоляцию тенантов, проверку прав внутри сервиса, вычисленный вручную
