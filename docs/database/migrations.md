# Миграции

## Формат

`backend/internal/migrations/NNNN_name.up.sql` и `NNNN_name.down.sql`. Пары
встроены в бинарник (`embed.go`), применяются командой `-migrate` у API и через
`make migrate`. Драйвер — `golang-migrate`, таблица версии — `schema_migrations`.

Правила:

1. **Только вперёд и вниз парой.** Миграция без `down` не принимается: она делает
   откат невозможным.
2. **Никогда не переписывать применённую миграцию.** Правка «по месту» разойдётся с
   уже развёрнутыми базами. Нужна правка — новая миграция.
3. **Идемпотентность.** Повторный `-migrate` — no-op, а не ошибка.
4. **Данные и схема разделены.** Заполнение (seed) — отдельные миграции
   (`0004_rbac_seed`, `0006_seed_webhooks_manage`, `0010_seed_agent_permissions`,
   `0013_seed_workflow_permissions`), чтобы каталог прав обновлялся предсказуемо.
5. **Имя отражает намерение**, а не номер задачи.

## Порядок применения

| Сценарий | Процедура | Проверка |
| --- | --- | --- |
| Чистая установка | `make migrate` на пустой БД | CI: «Migrations apply cleanly on an empty database» |
| Обновление существующей | тот же `-migrate`, версия поднимается шаг за шагом | CI job `upgrade-path` (см. `portability.yml`) |
| Повторный запуск | второй `-migrate` | CI: второй запуск обязан быть no-op |
| Откат | `-migrate` не откатывает; `down`-файлы для ручного разбора | Описано в [backup-restore.md](backup-restore.md) |

## Осознанные ограничения

- Откат миграции в проде не автоматизирован: цена ошибки выше, чем выгода. Путь
  восстановления — резервная копия.
- Миграции выполняются одним процессом (API при старте или `make migrate`), не
  репликами: одновременный запуск небезопасен, поэтому `-migrate` — отдельный шаг,
  а не автоматика при старте (`FORGECRM_MIGRATE_ON_START` по умолчанию выключен).
