# AI Workspace 2.0 — аудит и план реализации

Срез: 2026-11-07, после интеграции исправлений AI status и MCP в `main`. Это
архитектурный план, а не заявление о готовности продукта. Проверка провайдера и
production отдельно отмечены ниже.

## Карта существующих компонентов

```text
React App (/app/ai + плавающая кнопка)
  AiAssistantChat -> assistantCrm.ts -> AI completion / MCP read / agent proposal
                                       |
Go API: auth/session + CSRF + RBAC + tenant scope
  /ai/tasks, /ai/stream/* -> ai.Service -> Provider (Ollama/OpenAI-compatible)
  /mcp, /mcp/call, /mcp/tools -> ToolRegistry -> CRM services -> PostgreSQL
  /agent/* -> agent.Service -> approval -> AgentExecutor -> ToolRegistry -> CRM
  /mcp/credentials/* -> mcpcred.Service -> scoped MCP identity
  /documents/* -> storage -> object store + PostgreSQL metadata
  notifications -> notify / jobs / worker
```

Репозиторий представляет собой модульный монолит с отдельными процессами API и
worker; не следует создавать второй CRM-домен или новый обходной путь в БД.

## Проверка модели OpenRouter

Каталог OpenRouter на дату аудита перечисляет бесплатную модель
[`nvidia/nemotron-3-ultra-550b-a55b:free`](https://openrouter.ai/nvidia/nemotron-3-ultra-550b-a55b:free),
в том числе поддержку tool calling. Наличие карточки не доказывает успешный
авторизованный запрос, доступность провайдера в момент запуска, квоту конкретного
ключа или устойчивый streaming. Этот вызов ещё не выполнялся. Бесплатный тариф
имеет лимиты. В CI использовать локальный mock HTTP provider, не внешний endpoint.

Конфигурация проекта уже использует `FORGECRM_AI_*`, `OPENROUTER_API_KEY`,
`LLM_MODEL` и `LLM_BASE_URL`; запрошенные имена `AI_*` пока не являются
подтверждённым интерфейсом. Не рекламировать их до реализации и тестов.

## Целевые границы и инварианты

1. Сервис разговоров — единственный серверный источник истины для полного окна и
   плавающего Copilot; frontend cache не является хранилищем. Изоляция по tenant и
   владельцу, не только по UUID. Содержимое истории и технический аудит разделены.
2. Durable state агента и streaming — разные вещи: соединение SSE лишь наблюдает
   состояние; обрыв не должен незаметно выполнить повтор операции. Устойчивая
   обработка требует явной модели задач/аренды и идемпотентности, а не фоновой
   горутины на время HTTP-запроса. Сначала определить семантику отмены и recovery.
3. Модель и CRM/document content недоверенные. Tool call, включая аргументы,
   проверяется на сервере; полномочия берутся только из текущего principal.
   Записи проходят существующий agent approval, а не model-supplied `confirm`.
4. Для WRITE фиксировать исходную версию/состояние и точный diff; при исполнении
   атомарно проверять актуальность и полномочия. Массовые изменения, внешние
   эффекты и повторы проектировать отдельно; не предполагать exactly-once там,
   где этого не обеспечивает транзакция/идемпотентность.
5. Выбор CRM-контекста повторно проверяется на каждом чтении; нельзя раскрывать
   ранее сохранённый контекст после отзыва доступа. Сводки/память требуют явной
   политики хранения/удаления и защиты от межсессионного/межтенантного доступа.
6. Файлы: доступ владельца разговора плюс текущие права на источник, лимиты,
   безопасные парсеры, никакого исполнения содержимого. Сначала изолированные
   тестовые файлы; не импортировать производство в тестовый harness.
7. Аналитика возвращает период, числовые единицы/валюты и метод расчёта; не
   выдаёт ограниченную страницу или смешанные валюты за общий итог.

## Порядок этапов и предполагаемые файлы

Каждый этап требует миграции/контрактов по мере необходимости, тестов, проверки
изоляции и обновления документации. Список предварительный; пути и номера
миграций уточнять по актуальному коду, не создавать запланированные сущности
без реального использования.

1. **Аудит и план** — этот документ, `docs/index.md`; отдельная задача: устранить
   хранение текста запроса в техническом AI-журнале и проверить совместимость.
2. **Сессии и сообщения** — начата серверная основа: миграция 0040 и приватное
   хранилище в `backend/internal/ai/conversations.go`, с проверкой владельца,
   организации и `ai.tools.execute`. Пока это внутренний сервис без HTTP API,
   подключения Copilot или вызова модели: история в интерфейсе ещё не сохраняется.
   Далее нужны обработчики в `backend/internal/api`, регистрация `server.go` и `contract.go`,
   сгенерированный OpenAPI; тесты owner/tenant/IDOR/архив/удаление/конкуренция.
   Базовую модель `ai_conversations` и `ai_messages` вводить раньше tool calls,
   attachments и summaries, когда появится соответствующая логика.
3. **Workspace + общий плавающий интерфейс** — `frontend/src/pages/AiPage.tsx`,
   `components/AiAssistant*`, новый общий слой API/состояния, i18n, responsive и
   accessibility tests. Не показывать неработающие вложения и кнопки.
4. **Провайдер и streaming** — `internal/ai/{ai,streaming}.go`, API stream,
   mock provider tests, frontend streaming client. Tool calling и SSE должны иметь
   протокол сохранения частичных/финальных сообщений и отмены. ENV и docs только
   для действительно поддерживаемых параметров.
5. **Контекст и память** — отдельные versioned summaries, лимиты и политика
   просмотра/удаления, строгая переавторизация CRM-источников, тесты утечек.
6. **MCP** — добавлять реальные read/write инструменты по категориям через
   `crm`/analytics и явные permission/risk mappings; проверять scope и контракты.
7–8. **Агент и approval** — `internal/agent`, jobs/worker и `ai/agent_executor.go`;
   устойчивый журнал шагов, бюджеты, cancellation и idempotency, stale-write
   checks; tests на ревокацию прав, повторы и частичные сбои.
9–10. **CRM-контекст, аналитика, файлы** — переиспользовать `crm`, `analytics`,
   `storage` и безопасные парсеры `importx`; определить источники и доступ,
   тестировать ограниченные контексты и недоверенные документы.
11. **Администрирование** — расширять существующие config и `mcpcred` lifecycle;
   сохранять секреты на сервере, политики должны реально применяться.
12. **Security / CI / docs** — изолированная PostgreSQL + mock provider, frontend,
   E2E, миграции, доступность, replay и IDOR; `AGENTS.md`, `README.md`, архитектура,
   security, модульная и API-документация, факты и генерация OpenAPI.

## Непроверенное и deployment

Предыдущий PR с исправлениями статусного экрана имел успешные backend integration,
frontend и E2E, но визуальная проверка падала. После обновления визуального эталона
все проверки CI коммита `3424b3e` в `main` прошли; это не относится автоматически
к дальнейшим изменениям. Документ `FORGECRM_BLITZ_WAKE_ANALYSIS.md` фиксирует исчерпанную квоту
сборки Blitz на момент проверки, поэтому слияние кода само по себе не доказывает
доступность актуального production. Выполнение запросов к реальному OpenRouter и
работа со всей production CRM этим аудитом не подтверждены.
