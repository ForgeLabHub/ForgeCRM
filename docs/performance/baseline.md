# Производительность: базовая линия

Это **записанное измерение**, а не гейт. Ни один бенчмарк не валит CI, когда
число меняется: смысл документа в том, чтобы иметь воспроизводимую точку
отсчёта и способ перемерить её до и после изменения.

Числа ниже — снимок на коммит, а не обещание. Другой процессор, другая версия
PostgreSQL или другой размер `shared_buffers` дадут другие абсолютные значения;
сравнивать нужно прогоны на одной и той же машине.

## Что и зачем измеряется

Бенчмарки живут в `backend/internal/api/bench_test.go` и используют тот же
интеграционный стенд, что и корректностные тесты: реальный HTTP-сервер, реальный
PostgreSQL, реальные сессии и RBAC. Измеряется путь целиком — разбор запроса,
разрешение принципала, SQL, сериализация ответа, — а не только запрос.

Три группы:

| Группа | Что покрывает |
| --- | --- |
| `BenchmarkReadPaths` | список и поиск контактов, загрузка одной записи, глобальный поиск, админ-метрики |
| `BenchmarkWritePaths` | создание контакта (транзакция + outbox + аудит) и запись в outbox отдельно |
| `BenchmarkBackgroundWork` | слив outbox, круговой рейс очереди задач, полный импорт CSV |

## Как воспроизвести

Нужна **отдельная черновая база**: бенчмарки сбрасывают схему и засевают десятки
тысяч строк. Стенд отказывается работать, если имя базы не помечено как черновое
(`bench`, `test`, `scratch`, `ci`).

```bash
# один раз: база под бенчмарки
createdb -h 127.0.0.1 -U forgecrm forgecrm_bench

make test-bench
```

Масштаб данных задаётся переменной: `FORGECRM_BENCH_CONTACTS=200000 make test-bench`
воспроизводит масштаб, на котором измерялась миграция 0030.

| Параметр | Значение |
| --- | --- |
| CPU | AMD EPYC 9B14, 4 vCPU |

## Базовая линия

Измерено на `abc57d2` (`feat(worker): heartbeat table and workers_alive metric`),
`go test -tags=integration -run '^$' -bench . -benchmem -benchtime=3s ./internal/api/`:

| Бенчмарк | нс/оп | B/оп | allocs/оп |
| --- | ---: | ---: | ---: |
| `ReadPaths/contacts_list_search_selective` | 145 009 510 | 47 427 | 808 |
| `ReadPaths/contacts_list_search_broad` | 49 485 843 | 171 231 | 2 273 |
| `ReadPaths/contacts_list_first_page` | 7 740 395 | 168 956 | 2 254 |
| `ReadPaths/get_contact` | 1 470 597 | 39 013 | 720 |
| `ReadPaths/global_search` | 110 323 694 | 41 731 | 789 |
| `ReadPaths/admin_metrics` | 2 072 793 | 40 683 | 721 |
| `WritePaths/create_contact` | 2 775 394 | 45 913 | 886 |
| `WritePaths/outbox_emit` | 639 009 | 1 331 | 33 |
| `BackgroundWork/outbox_claim_and_publish` | 63 116 478 | 154 445 | 3 427 |
| `BackgroundWork/jobs_enqueue_claim_complete` | 1 950 228 | 9 551 | 165 |
| `BackgroundWork/import_csv_execute` | 556 205 362 | 49 560 598 | 920 554 |

## Что эти числа показывают

**Триграммный индекс не спасает `count(*)` при поиске по трём колонкам.**
`contacts_list_search_selective` — 145 мс на HTTP-запрос, который находит одну
строку. Причина не в отсутствии индекса, а в том, что условие — это `OR` по трём
`ILIKE`, и планировщик не может сложить три битмапа в один дешёвый план. Проверка
`EXPLAIN (ANALYZE, BUFFERS)` на том же наборе, только `count(*)` с тем же
условием:

- отдельная ветка `email ILIKE '%…%'` → Bitmap Index Scan по
  `contacts_email_trgm_idx`, 4,8 мс;
- всё условие целиком (три ветки `OR`) → **Seq Scan**, 73 мс, `Rows Removed by
  Filter: 49999`;
- `SET enable_seqscan=off` не помогает: вместо этого выбирается Index Scan по
  `contacts_active_idx`, который всё равно читает 50 000 строк и отсеивает
  49 999 — 75 мс, то есть не быстрее.

То есть на 50 000 контактов поиск по одному совпадению стоит как полный скан
таблицы. Это записанный факт базовой линии, а не регрессия: следующий шаг, если
производительность поиска станет приоритетом, — выражение `tsvector` с GIN-индексом
вместо трёх независимых триграммных индексов. Здесь это только измеряется.

**`global_search` стоит как шесть поисковых запросов** — по одному на каждый
читаемый тип сущности. 110 мс на запрос согласуется с этим: он не может быть
дешевле самого дорогого из шести.

**`get_contact` и `admin_metrics` — единицы миллисекунд**, потому что попадают в
индекс по первичному ключу и в дешёвые `count(*)`. Это ожидаемая форма.

**Запись дешевле чтения.** `create_contact` — 2,8 мс, `outbox_emit` — 0,6 мс.
Транзакционная запись в outbox добавляет к мутации около 0,6 мс — это цена
гарантии доставки, и она не является узким местом.

**Импорт CSV обрабатывает строку за ~0,11 мс**: 556 мс на полный цикл из 5 000
строк — создание задания, разбор, валидация, вставка и запуск через worker. Это
самая тяжёлая одиночная операция в продукте, и её цена растёт линейно по строкам.

## Что здесь не измеряется

- Нагрузка под конкуренцией: бенчмарки однопоточные, `-cpu` не задан.
- Поведение под реальным профилем трафика — это записано в
  [verification/matrix.md](../verification/matrix.md) как сознательно не
  проверяемое автоматически.
- Время холодного старта, потребление памяти процессом, размер индексов.

## Как обновлять

1. Перезапустить `make test-bench` на том же стенде.
2. Если числа сдвинулись, заменить таблицу и добавить строку «измерено на
   `<commit>`» — старые значения не переписываются задним числом, а заменяются
   вместе с указанием коммита.
3. Если изменился стенд (PostgreSQL, `shared_buffers`, машина), это указывается
   в таблице «Стенд»: иначе сравнение с предыдущим снимком бессмысленно.
