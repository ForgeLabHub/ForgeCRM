# Аудит SSO: Authentik / OIDC для ForgeCRM

Дата: 4 ноября 2026 г. Проверка ветки `arena/5fd3022f-forgecrm` начата на `6ac40e71b8d30d035cde8c7d24f633fe9dbcbc88`. Файл описывает проверенную архитектуру и план, а не включённый сервис. Production, его окружение и база не изменялись; реальные секреты и ресурсы не создавались.

## Вердикт

**Не включать SSO в production в текущем состоянии.** Существующий OIDC-модуль — полезная основа, но он автоматически связывает существующие аккаунты по подтверждённому email, что прямо противоречит поставленному требованию. Кроме того, авторизационный `state` не привязан к браузеру, начавшему flow, и обнаружены вопросы tenant isolation управления провайдерами. Существующего безопасного пользовательского сценария явной привязки identity в проекте не найдено. Простой настройкой Authentik эти проблемы не устранить.

Для полноценной реализации нужны изменения аутентификации, независимые security review, реальные PostgreSQL-тесты и mock OIDC provider-тесты. В этом изменении **новый SSO-модуль не объявляется реализованным**: небезопасное автоматическое связывание не отключено, существующая авторизация и работающие конфигурации намеренно не изменены. Нельзя считать эту страницу инструкцией включения до выполнения блокирующих условий ниже.

## 1. Текущее состояние авторизации

- Локальный вход по email и паролю, MFA и сессии находятся в `backend/internal/authn` и API auth handlers. Сессия серверная, её токен хранится в cookie, в базе сохраняется hash. Доступы проверяются существующим RBAC и текущим членством в организации. Сохранить локальный вход как аварийный и не отключать его.
- `backend/internal/oidc` уже содержит vendor-neutral OIDC Authorization Code flow, discovery, PKCE S256, nonce, проверку ID token через `github.com/coreos/go-oidc/v3` и `golang.org/x/oauth2`. Это не пустой модуль и не SAML-реализация. Зависимости поддерживают OIDC-провайдеры в общем случае, но отдельная совместимость с Authentik, Microsoft или Google не доказана.
- `0022_sso_oidc` создала `oidc_providers`, `user_identities`, `oidc_login_states`; OAuth client secret провайдера, записанный через управление, шифруется keyring. Админ-интерфейс `frontend/src/pages/admin/SSOPage.tsx` и публичный список провайдеров уже существуют. `sso.manage` управляет провайдерами.
- `Begin` генерирует state/nonce/PKCE; `Complete` однократно атомарно помечает state использованным и проверяет подпись, issuer, audience, срок и nonce ID token. Эти проверки полезны, но не заменяют browser binding и контроль привязки. При успешном SSO создаётся обычная сессия `authn`, записываются события аудита.
- Действующая архитектура содержит SAML как возможный канал Authentik/Keycloak, но отдельного SAML SP-модуля ForgeCRM в проверенном backend/frontend не найдено. Он не требуется для OIDC.

## 2. Блокирующие дефекты и ограничения

1. **Автопривязка по email.** `resolveIdentity` при отсутствии `(provider_id, subject)` ищет пользователя по подтверждённому email и вставляет `user_identities`. Выключение JIT этому не препятствует. Доменное ограничение и `email_verified` не являются доказательством согласия владельца локального аккаунта. Нужен явный flow связывания после подтверждённого входа в существующий аккаунт либо отдельное безопасное администраторское согласование; автоматическое связывание по email запретить.
2. **State не связан с инициировавшим браузером.** Он случайный, истекает и одноразово потребляется из БД, но `handleOIDCStart` не записывает браузерную связку, а callback не сверяет её. Это не обеспечивает защиту от login CSRF/session swapping. Нужна привязка к случайному защищённому `HttpOnly`, `Secure`, `SameSite=Lax` короткоживущему cookie (или равноценному серверному механизму), сравнение до потребления state, очистка и тесты для разных браузеров и повтора. Не ослаблять обычный CSRF.
3. **Провайдер и tenant scope.** `resolveByKey` выбирает провайдера по ключу без tenant-предиката; уникальность ключа в схеме ограничена областью провайдера, поэтому одно имя может существовать в нескольких организациях. Обработчик создания принимает непустой `organization_id`, а update/delete работают по ID без проверенной в этих вызовах tenant-фильтрации. Нужны серверные проверки границ для create/update/delete и однозначный выбор провайдера, тесты перекрёстного доступа и переключения организации. Нельзя считать роль `sso.manage` разрешением менять чужого провайдера.
4. **Модель членства и MFA.** При существующей identity разрешается первое активное членство, не обязательно организация провайдера. `IssueSSOSession` отмечает сессию как MFA verified без проверки `acr`/`amr`; политику доверия MFA со стороны IdP и связь провайдера с разрешённой организацией нужно определить и протестировать. Блокировку/удаление пользователей и членств проверять при каждой выдаче сессии.
5. **Провайдерская сеть.** Discovery использует обычный HTTP-клиент, допускающий приватные адреса, поскольку issuer считается доверенной настройкой. Управление провайдерами должно быть ограничено и защищено от SSRF и небезопасного discovery/redirect; нужны явно определённые правила для внутреннего Authentik и публичных OIDC.
6. Сохранённый в `oidc_login_states` `return_to` не извлекается при `Complete`; callback читает и отдельно проверяет `return_to` из собственного query. Это не проверенная end-to-end семантика возврата. Код ошибки провайдера и описание записываются в лог: обеспечить безопасную фильтрацию/минимизацию логов до production.
7. OIDC entrypoint создаёт ссылку автоматически только из UI выбора провайдера; зарегистрированных маршрутов безопасной ручной привязки пользователя к subject не найдено. Не обходить это ручными SQL-вставками в production.

Существующие тесты `backend/internal/api/sso_integration_test.go` содержат локальный fake provider с discovery/JWKS и подписанными ID-токенами, но наличие тестов не доказывает выполнение новых требований выше. Требуются отрицательные тесты по всем пунктам и отказ от прежних сценариев автосвязывания.

## 3. Что изменено в этой работе

- Проведён анализ текущего кода и документации; SSO-сервис, локальный парольный вход, RBAC и production не изменены.
- В `.env.example` синтаксис `FORGECRM_OIDC_SCOPES` исправлен на строку с пробелами в кавычках: загрузчик использует `strings.Fields`, а не разделение по запятой. Однако поля конкретного провайдера берутся из его записи в БД; глобальная строка scopes не создаёт провайдера и не является доказанным способом задать scopes конкретного flow.
- Миграций SSO и новых SSO ENV не добавлено. Миграция `0032_telegram_link_codes` относится только к Telegram и к Authentik не относится.
- Реальный сервер Authentik не развёрнут, взаимная интеграция с ForgeCRM не тестировалась. Никакие реальные учётные данные не создавались.

## 5. Authentik и Keycloak: бесплатность и инфраструктура

| Критерий | Authentik | Keycloak |
| --- | --- | --- |
| ПО | Open-source core бесплатен, есть отдельные платные Enterprise-функции и поддержка. Для базового OIDC не требуется оформлять платный сервис. [Источник](https://goauthentik.io/pricing/). | Open-source IdP; базовое self-hosting и OIDC без обязательной лицензии на ПО. [Источник](https://www.keycloak.org/). |
| CPU/RAM | Официальная инструкция Compose для test/small production указывает **не менее 2 CPU cores и 2 GB RAM** на хост, плюс Docker/Podman Compose v2. Это не гарантия надёжной production-ёмкости. [Источник](https://docs.goauthentik.io/install-config/install/docker-compose/). | Зависит от нагрузки и конфигурации. Официальный sizing HA приводит 1250 MB на Pod с указанными cache/session допущениями и примеры CPU; это не универсальный минимум или бюджет для всего стека. [Источник](https://www.keycloak.org/high-availability/single-cluster/concepts-memory-and-cpu-sizing). |
| Хранение | В актуальной документации указан PostgreSQL для данных и фоновых задач; конкретные поддерживаемые версии зависят от выбранной версии продукта. [Источник](https://docs.goauthentik.io/install-config/configuration). | Поддерживает внешнюю production-БД; размер зависит от deployment. |
| Где запускать | Нужны постоянно доступные server и worker, собственные данные/backup, HTTPS и надёжный DNS. Отдельная машина не является технической обязанностью, но изоляция и достаточные ресурсы обязательны. | Аналогично: отдельный хост необязателен технически, но требует ресурсов, БД, HTTPS и эксплуатации. |
| Цена эксплуатации | Бесплатное ПО **не означает** бесплатную вычислительную инфраструктуру, домен, резервные копии и работу администратора. | То же. |

Репозиторное руководство Blitz описывает 512 МБ на бесплатном тарифе для ForgeCRM и засыпание API; текущие квоты аккаунта, возможности хостинга дополнительных частей, сети, постоянного хранения и реальная цена **не проверены**. На этой основе нельзя обещать, что Authentik с его минимальными требованиями безопасно поместится бесплатно в том же размещении. Владелец должен проверить актуальные лимиты и выбрать собственную подходящую инфраструктуру; без этого запуск Authentik здесь не производится. Отдельная БД/схема и учётная запись для данных IdP могут потребоваться для изоляции и backup; ForgeCRM PostgreSQL остаётся её источником данных CRM, миграция CRM на другую БД не предлагается.

## 6. Существующие ENV ForgeCRM

Все значения ниже — конфигурация *после исправления блокеров и в отдельном тестовом окружении*. Env считывается при старте, поэтому его изменение требует обновления окружения и перезапуска соответствующего процесса. **Не менять действующий `FORGECRM_SECRET_KEY`**, не отправлять секреты в чат и не встраивать их в frontend.

| Точное имя | Назначение в текущем коде | Статус |
| --- | --- | --- |
| `FORGECRM_OIDC_ENABLED` | Включает OIDC-сервис; `false` по умолчанию. | Для тестового включения после исправлений — `true`; сейчас не включать. |
| `FORGECRM_OIDC_ISSUER` | Поле глобального конфига, обязательное для валидации при включённом флаге. Само по себе не создаёт провайдера в БД. | После настройки взять точный issuer из discovery Authentik; без фиктивного значения. |
| `FORGECRM_OIDC_CLIENT_ID` | Поле глобального конфига, требуемое валидатором; фактический OAuth flow читает client ID из записи `oidc_providers`. | Необходимо для запуска при включённом флаге и отдельно в записи провайдера. |
| `FORGECRM_OIDC_CLIENT_SECRET` | Загружается в общий config, но flow использует client secret из зашифрованной записи провайдера. | Не считать env достаточным для настройки secret провайдера; не записывать реальные секреты в `.env.example`. |
| `FORGECRM_OIDC_REDIRECT_URL` | Явный callback; иначе `FORGECRM_BASE_URL` + `/api/v1/auth/oidc/callback`. | Для production-проекта по заданному origin это `https://forgecrm.forgecrm.blitz.cloud/api/v1/auth/oidc/callback`, только после исправлений и согласованного deployment. |
| `FORGECRM_OIDC_SCOPES` | Разбирается по пробелам в config; provider flow использует scopes записи провайдера, с дефолтом `openid email profile`. | Текущий пример quoted; на конфигурацию записи провайдера полагаться отдельно. |
| `FORGECRM_BASE_URL` | Origin приложения для fallback callback. | Существующий, не заменять без проверки. |
| `FORGECRM_SECRET_KEY` | Ключ платформы для зашифрованных секретов и CSRF. | Существующий стабильный секрет, не ротировать в рамках этой задачи. |
| `FORGECRM_DATABASE_URL` / `DATABASE_URL` | Основная PostgreSQL ForgeCRM. | Существующая Blitz PostgreSQL; не заменять на БД Authentik. |
| `FORGECRM_ENV`, `FORGECRM_COOKIE_SECURE` | Production-валидация и защищённые cookie. | В production необходимы production и secure cookie; фактические значения неизвестны. |

Установка env недостаточна: нужен OIDC provider в БД через защищённый admin UI/API, с отдельным `issuer`, `client_id`, client secret, scopes, областью организации и политикой. `FORGECRM_OIDC_ENABLED=false` позволяет оставить обычный вход, но состояние и сохранённые записи текущего production здесь не проверены.

Отдельно Authentik имеет собственные переменные и секреты, не являющиеся переменными ForgeCRM: текущий официальный Compose использует `PG_PASS` и `AUTHENTIK_SECRET_KEY`, а его PostgreSQL-настройки описаны в документации Authentik. Версия дистрибутива может менять состав ENV: выбирать по официальной инструкции выбранного релиза, не копировать значения и не делиться ими. Ресурсы, ключи и контейнеры на этапе аудита не создавались.

## 7. План настройки Authentik владельцем после исправления блокеров

1. Подготовить изолированный тестовый сервер с достаточными ресурсами по [официальной инструкции Compose](https://docs.goauthentik.io/install-config/install/docker-compose/); обеспечить HTTPS, DNS, постоянное хранение и безопасные резервные копии IdP. Проверить актуальные расходы. Действия со стартом контейнеров и созданием секретов отдельно согласуются владельцем, здесь не выполнялись.
2. В Authentik создать тестовое приложение и OAuth2/OIDC provider, выбрать authorization code и конфиденциальный клиент, разрешить PKCE S256, `openid`, `email`, `profile` и ключ подписи. Ограничить доступ тестовой группой. Выбрать точный **strict** redirect URI, соответствующий тестовому ForgeCRM; production callback указан выше лишь для будущего использования. Сверять настройки с документацией конкретной версии Authentik.
3. Взять **issuer** из discovery document созданного приложения, проверить совпадение issuer и доступность JWKS по HTTPS из backend. Получить client ID и secret только владельцу; не копировать секрет в отчёты/логи.
4. После реализации безопасного user-consented identity linking настроить provider в ForgeCRM в нужной организации, отключить JIT до отдельного решения и протестировать явную привязку по `(issuer/provider, subject)` — никогда только по email. Текущее отключение JIT **не устраняет** автопривязку, поэтому сейчас шаг заблокирован.
5. На тестовом стенде проверить корректный flow, отказ по issuer/audience/signature/expiry/nonce/state, другой браузер и replay, истёкшую попытку, неподтверждённую привязку, конфликты email, отозванное членство, другую организацию, MFA policy и сохранность password login. Выполнить реальные PostgreSQL tests и независимый security review.
6. После успешных проверок и отдельного разрешения владелец может планировать deployment и включение SSO. Проверить аварийный вход локального администратора и rollback. Microsoft/Google добавлять как отдельные OIDC providers только после тех же проверок и с явным подтверждением identity.

## 8. Что остаётся владельцу и что нельзя сделать сейчас

Владелец выбирает и оплачивает, если необходимо, подходящую инфраструктуру и DNS, создаёт Authentik и credentials, определяет политику пользователей/MFA, подтверждает сопоставления идентичностей и разрешает rollout. Пока не реализованы устранение перечисленных блокеров, тестовый контур и безопасный linking flow, реально работающее и безопасное SSO Authentik для этого проекта не подтверждено. В рамках аудита сервер не создавался, production env и база не менялись, deployment не выполнялся.
