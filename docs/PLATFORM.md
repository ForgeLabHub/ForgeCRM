# Платформа ForgeLabHub и ForgeCRM

Этот документ отвечает на два вопроса, которые остальные документы
предполагают уже решёнными: **что такое ForgeLabHub и ForgeCRM как продукт** и
**что именно отличает платформу от обычной CRM**. Числа здесь — измеренное
состояние кода; машинно-проверяемая сводка живёт в
[verification/project-facts.md](verification/project-facts.md), а утверждение с
командой и заданием CI — в [verification/matrix.md](verification/matrix.md).

## 1. Что такое ForgeLabHub и ForgeCRM

**ForgeLabHub** — это зонтик: лаборатория самостоятельных бизнес-платформ. Она
строит не «CRM с модулями», а единую основу, на которой собирается много
бизнес-решений, и первым таким решением является ForgeCRM.

**ForgeCRM** — самостоятельная бизнес-платформа: CRM, автоматизация, аналитика,
ИИ, риски, прогнозирование, симуляции, документы, интеграции, безопасность и
аудит на общей инфраструктуре. Ядро работает само по себе — без провайдера ИИ,
без внешних API и без включённых опциональных интеграций. Каждая интеграция
включается отдельно.

Три уровня платформы:

| Уровень | Что входит |
| --- | --- |
| **Бизнес-приложения** | CRM и продажи, поддержка, задачи и проекты, BI и отчёты, риск, workflow, документы, Simulation Lab |
| **Сервисы платформы** | Идентификация, организации, авторизация, runtime workflow, аналитика, оркестратор ИИ, уведомления, интеграции, аудит, файлы, импорт/экспорт, поиск |
| **Инфраструктура** | PostgreSQL, Redis, брокер событий, S3-совместимое хранилище, обратный прокси, наблюдаемость, секреты, развёртывание |

### Режимы работы

| Режим | Что это значит в этом репозитории |
| --- | --- |
| **Single Node** | Всё поднимается одной командой `./forge.sh start` через Docker Compose на одном сервере или ПК; Kubernetes не требуется |
| **Distributed** | Stateless-сервисы масштабируются горизонтально: `docker-compose.multireplica.yml` и независимый CI-прогон `multi-replica-verify`; БД, брокер и S3 могут быть внешними |
| **Microservices-ready** | Границы сервисов и контракты готовы к выделению, но монолит не дробится ради количества. Готовность **проверяема**, а не документальна: см. раздел 3 |
| **Multi-tenant** | Каждый запрос, событие, задача, контекст ИИ и файл привязаны к организации; фильтр `organization_id` обязателен |
| **API-first** | OpenAPI 3.1 генерируется из живого роутера; фронтенд использует типизированный клиент |
| **Secure by default** | RBAC на сервере, изоляция тенантов, неизменяемый аудит, безопасные загрузки, секреты вне Git |

### Про микросервисы честно

Платформа реализована как **модульный монолит с проверяемыми границами**, а не
как россыпь из двух десятков контейнеров. Это осознанный выбор, а не упрощение:
границы сервисов существуют в виде пакетов, контрактов и собственных миграций, и
набор `scripts/extract-test` доказывает, что модуль **действительно**
выделяется в отдельный Go-модуль, собирается, проходит тесты и запускает
свой `cmd/smoke`. Дробление начинается тогда, когда у модуля появляется
самостоятельная ответственность, нагрузка или независимый релизный цикл, — а не
заранее.

## 2. Границы сервисов

Каждый домен владеет своей схемой и своими миграциями; прямые запросы к таблицам
другого домена запрещены; ссылки между доменами — по идентификатору и контракту.
Границы и правила зависимостей описаны в
[architecture/components.md](architecture/components.md) и
[architecture/dependency-rules.md](architecture/dependency-rules.md); карта
пакетов и её проблемы — в [DEPENDENCY_MAP.md](DEPENDENCY_MAP.md).

| Домен | Ответственность | Ключевые события |
| --- | --- | --- |
| Идентификация | Пользователи, вход, сессии, приглашения, OIDC | `user.invited`, `session.revoked` |
| Организации | Организации, команды, участники, настройки, лимиты | `organization.created`, `member.added` |
| Авторизация | RBAC, разрешения, проверки политик, изоляция тенантов | `permission.denied` |
| CRM | Клиенты, контакты, лиды, сделки, воронки, заметки, активности, кастомные поля, сегменты, дубли | `customer.*`, `deal.*`, `lead.*` |
| Задачи | Задачи, подзадачи, проекты, статусы, дедлайны, повторения, зависимости | `task.created`, `task.overdue`, `task.completed` |
| Workflow | Редактор, версии, публикация, runtime, повтор, согласование | `workflow.started/completed/failed` |
| Уведомления | Email, in-app, шаблоны, настройки, журнал доставки | `notification.sent/failed` |
| Аналитика | Метрики, дашборды, отчёты, агрегаты, экспорт, расписания | `analytics.report.ready` |
| Интеллект | Оркестратор ИИ, контекст, RAG, агенты, лимиты, fallback | `ai.request.completed/failed` |
| Риск | Оценки риска, факторы, объяснения, приоритизация | `risk.calculated` |
| Прогнозирование | Прогнозы выручки, продаж, нагрузки, удержания; версии и качество | `forecast.created` |
| Симуляции | Сценарии, параметры, запуск, сравнение, чувствительность | `simulation.completed` |
| Документы | Документы, версии, OCR, извлечение сущностей, сроки хранения | `document.uploaded/analyzed` |
| Поиск | Глобальный поиск с учётом прав | `search.index.updated` |
| Интеграции | Каталог, OAuth/ключи, синхронизация, ошибки | `integration.connected/failed` |
| Вебхуки | Подписки, подпись, доставка, повтор, журнал | `webhook.delivery_failed` |
| Аудит | Аудит действий и безопасности, неизменяемый журнал | `audit.recorded` |
| Файлы | Метаданные файлов, операции S3, безопасные загрузки | `file.uploaded/deleted` |
| Импорт/экспорт | Импорт, экспорт, валидация, отчёты об ошибках | `import.completed`, `export.ready` |

Словарь событий — единственный источник истины `outbox.EventTypes()`,
публикуемый как `event_types` на `GET /api/v1/system/capabilities`; подписка на
вебхуки читает его, а не локальную константу.

## 3. Готовность к выделению проверяема

Утверждение «модуль готов к выделению» в этом репозитории — не строчка в
документе, а проходящая проверка:

- `scripts/extract-test/<module>/setup.sh` копирует **только собственные** файлы
  пакета в чистый Go-модуль, собирает его, прогоняет его тесты и запускает
  `cmd/smoke`. Скрытая зависимость всплывает как ошибка компиляции.
- Модуль попадает в `scripts/extract-test/modules.txt` **только когда выделение
  действительно проходит**; `scripts/extract-test/run.sh` прогоняет каждый
  перечисленный модуль, а в CI есть задание `extraction`.
- `TestExtractionBoundaryHolds` в `internal/archtest` обеспечивает ту же границу
  дёшево на каждом `go test ./...` и падает, когда закреплённого модуля нет в
  графе, — поэтому ни устаревшая проверка, ни пропущенное задание CI не могут
  скрыть нарушение.

Сегодня доказано **36** модулей (набор — источник истины; полный список в
[MODULES.md](MODULES.md) и [EXTRACT_READY.md](EXTRACT_READY.md)). Написание первых
тестов модуля само является шагом поиска багов: выделение `parsers`, например,
вскрыло, что XLSX отклонялся проверкой UTF-8, применённой ко всем форматам.

## 4. Шестнадцать ключевых возможностей

Ниже — то, что отличает платформу. Каждая возможность названа вместе с местом в
коде и проверкой, которая её удерживает.

### 1. Модульный монолит с проверяемыми границами выделения
36 доказанных модулей и `TestExtractionBoundaryHolds` на каждом `go test ./...`
превращают «готов к выделению» из обещания в проверку. Детали — в разделе 3.

### 2. Центр импорта с безопасной распаковкой недоверенных архивов
Парсеры CSV, TSV, JSON, JSONL, XLSX, XML и архивы ZIP, TAR, TAR.GZ/TGZ,
TAR.BZ2, TAR.XZ, GZIP, BZIP2, XZ. Распаковка живёт в `internal/importx/safe` и
защищена от обхода пути и «архивных бомб». Мастер ведёт от загрузки через
предпросмотр, сопоставление, валидацию и пробный прогон к исполнению, отчёту,
ошибкам и повтору. Код — `internal/importx`, проверки — в
[verification/matrix.md](verification/matrix.md).

### 3. Транзакционный outbox и идемпотентные потребители
Бизнес-изменение и событие пишутся в одной транзакции PostgreSQL, отдельный
publisher отправляет и помечает; потребители идемпотентны через inbox и ключ
дедупликации; есть повтор и DLQ. Прогоны workflow по событию дедуплицируются
ограничением базы (`workflow_run_events` с первичным ключом по
`(workflow_id, event_id)`), а не флагом, — иначе повтор доставки оставлял бы
осиротевший прогон.

### 4. Защита от SSRF в исходящих соединениях
`internal/netguard` и жизненный цикл адаптера в `internal/integrations`
проверяют адрес до соединения, поэтому интеграция и вебхук не могут обратиться к
внутренней сети. См. [security/threat-model.md](security/threat-model.md).

### 5. Workflow runtime, который обеспечивает права сам
Движок workflow вызывает `crm.Service` напрямую, минуя HTTP-middleware, поэтому
он сопоставляет каждый тип шага с `rbac.Permission` и проверяет его против
принципала автора до запуска шага. Workflow действует как свой автор,
определяемый **на момент исполнения**: заблокированный автор или отозванная роль
останавливают следующий прогон, а не замораживаются на строке workflow.

### 6. Human-in-the-loop согласования с подтверждением вторым фактором
Опасные действия агента создают согласование (`internal/agent`), а подтверждение
требует второго фактора (`step_up_handlers.go`). Просроченное согласование
переводит действие в `expired` и коммитит это состояние — сбой, который однажды
уже был, потому что запись и возврат ошибки жили в одной транзакции.

### 7. Контекстный ИИ без прямого доступа к базе
ИИ работает только через оркестратор и контролируемые tools
(`internal/ai`): адаптеры провайдеров (Ollama, совместимые с OpenAI),
маршрутизация, лимиты, таймауты, fallback и журналирование. Отказ ИИ не ломает
CRM. Контекстный ИИ появляется на карточках аккаунта, контакта, сделки, обращения
и задачи.

### 8. MCP-транспорт с правами и аудитом
`tools/list` и `tools/call` поверх JSON-RPC: инструменты чтения, аналитики и
ограниченной записи, каждый — с проверкой пользователя, изоляцией тенанта, RBAC и
аудитом. Возможность называется `tool_api`, а не «MCP-сервер», потому что она не
реализует ресурсы и промпты MCP.

### 9. Риск, прогнозирование и Simulation Lab
`internal/risk`, `internal/forecast`, `internal/simulate` считают риск, прогнозы
и сценарии. Эвристика выдаётся как эвристика с объяснением, а не как
калиброванная вероятность. Симуляция изолирована от production-данных, а
применение сценария — отдельная подтверждаемая операция.

### 10. Файлы на S3-совместимом хранилище с реконсиляцией
`internal/storage` и `internal/objectstore`: независимый от провайдера
`ObjectStore` (AWS, MinIO, Ceph, B2, Wasabi), ключи объектов строятся сервером,
права проверяются на каждом маршруте. Сверщик объектов и строк запускается
воркером на ежечасном такте обслуживания, поэтому осиротевший объект или строка
не остаются неверными навсегда.

### 11. Неизменяемый журнал аудита
Аудит «только добавление»: пользователь, который действовал, не может быть
удалён — каскад внешнего ключа блокируется триггером. Аккаунт вместо удаления
отключается (`status` — одно из `invited`, `active`, `suspended`, `blocked`).

### 12. RBAC и изоляция тенантов как проверяемые инварианты
103 разрешения в каталоге и 14 системных ролей; каталог и сид совпадают точно, а
`TestSeedDataMatchesThePermissionCatalog` ловит расхождение. Изоляция тенантов
проверяется тестами на IDOR и cross-tenant. Скрытие элемента интерфейса —
удобство, а не контроль доступа: права проверяются на сервере.

### 13. OpenAPI, генерируемый из живого роутера
`docs/api/openapi.json` генерируется из роутера и регистраций маршрутов
(`cmd/openapi-gen`) и **никогда не правится руками**; CI падает, когда документ
расходится с кодом. Схемы выводятся из типов, которые обработчики действительно
используют, поэтому документ не может описать форму, которую не принимает ни
один код. См. [api/conventions.md](api/conventions.md).

### 14. Мультитенантность как инвариант, а не как настройка
Каждый запрос с областью тенанта фильтрует по `organization_id`; каждое событие,
задача, контекст ИИ и файл привязаны к организации. Отдельная схема и миграции у
каждого домена, soft delete и хранение, оптимистичная блокировка, индексы под
`tenant + фильтры`, никаких cross-service внешних ключей.

### 15. Конструктор: рецепт превращается в рабочий проект
`forgecrm scaffold <recipe> --output <dir>` читает манифест рецепта, копирует
ровно названные модули из `internal/`, переписывает их импорты на путь модуля
проекта, отрисовывает шаблоны и пишет README — затем падает, если какой-либо
сгенерированный файл всё ещё называет ForgeCRM. Он никогда не перезаписывает
непустой каталог и сам себе проверка: `scripts/constructor-test/run.sh`
независимо собирает, тестирует и запускает сгенерированный проект. См.
[CONSTRUCTOR.md](CONSTRUCTOR.md).

### 16. Single Node → Distributed одной командой
`forge.sh` даёт `install`, `start`, `stop`, `restart`, `status`, `logs`,
`doctor`, `update`, `migrate`, `backup`, `restore`, `test`, `smoke`, `dev`,
`prod`, `scale`, `clean`. `doctor` диагностирует Docker, Compose, контейнеры,
порты, конфиг, PostgreSQL, миграции, брокер, S3, readiness, место и логи и
объясняет причину. Переносимость проверяется в CI: `backup-restore`,
`compose-smoke`, `upgrade-path`, `config-without-secrets` и
`multi-replica-verify`.

## 5. Безопасность, надёжность, наблюдаемость

Модель угроз и права — в [security/threat-model.md](security/threat-model.md) и
[security/permissions.md](security/permissions.md); эксплуатация и обновления — в
[operations/deployment.md](operations/deployment.md) и
[operations/upgrades.md](operations/upgrades.md).

Поведение при отказах:

| Отказ | Поведение |
| --- | --- |
| ИИ недоступен | CRM работает |
| Брокер недоступен | События не теряются через outbox |
| Воркер остановлен | API принимает допустимые запросы, задачи ждут |
| S3 недоступен | Понятная ошибка файловых операций |
| Аналитика недоступна | CRM работает |
| Экземпляр CRM упал | Другие работают (multi-replica) |
| Redis недоступен | Безопасная политика отказа |
| PostgreSQL недоступна | Сервисы not-ready |

Наблюдаемость: Prometheus-метрики, `/health` и `/ready`, correlation IDs,
структурные логи с редактированием секретов. В Single Node мониторинг — отдельный
профиль Compose.

## 6. Что осознанно вне границ

Чтобы документ не обещал больше, чем код:

- **Kubernetes не обязателен.** Развёртывание — Docker Compose.
- **PostgreSQL — единственное поддерживаемое хранилище.** MySQL/MariaDB не
  объявляется совместимым без тестов; измеренные блокеры зафиксированы в ADR 0008,
  а MySQL присутствует только как **источник** миграции.
- **Лицензия не выбрана.** Не добавляйте её без согласия владельца.
- **Отраслевые Case Packs, биллинг с платёжным провайдером, push-уведомления,
  ABAC/ReBAC, Gantt** — запланированы, но не реализованы; живые статусы — в
  [ROADMAP.md](ROADMAP.md) и [ACCEPTANCE_CRITERIA.md](ACCEPTANCE_CRITERIA.md).
- **Никаких фиктивных экранов.** Страница, которая ничего не делает, не
  считается выполненной возможностью.
