# ForgeCRM — исторический аудит production-переменных для Telegram

**Исторический снимок на 6ac40e7 / production 8d350b0**, 4 ноября 2026. Всё ниже описывает именно эти ревизии, а не состояние текущей ветки. В ветке позднее добавлены миграции 0032–0033, webhook и доставка; см. [актуальный статус](PHASE2_STATUS.md). Production и его конфигурация не изменялись, настройки и факт авторегистрации/автодеплоя неизвестны. Снимок не служит инструкцией по включению интеграции.

На момент аудита входящего webhook, команд, исходящей очереди и карточек в проверенной production-ревизии не было. Секреты и Bot API не проверялись; BotFather, Blitz и реальные чаты не изменялись. Готовность `/ready` не подтверждает Telegram.


## Как читать таблицы

- **Обязательность** относится к текущему коду, а не к недописанному модулю. «Условно» указывает, при какой функции требуется значение. «Дефолт» не доказывает, что переменная задана в Blitz.
- **Перезапуск**: конфигурация загружается при старте процесса. Изменение env требует пересоздания/перезапуска затронутых частей с новым окружением; обычного обновления страницы недостаточно. Будет ли Blitz делать это автоматически — проверить в интерфейсе платформы. Переменные сборки требуют пересборки.
- `<секрет>`, `<DSN из Blitz>` и аналогичные обозначения — **описания, не значения для копирования**. Не вставляйте их буквально. Примеры URL с `example.com` — несекретные примеры, не реальные endpoints проекта.

## Будущее объектное хранилище: не настраивать сейчас

Supabase-проект, по условию, отсутствует. Основная PostgreSQL остаётся на Blitz; вторую CRM-базу создавать не требуется. В коде есть отдельный S3-совместимый слой для вложений CRM, но **интеграция Telegram-медиа с Supabase не реализована и совместимость не проверена**. Значения ниже описывают существующий код, а не готовую инструкцию подключения Supabase.

`internal/objectstore/s3.go` при нормализации оставляет от URL только host и схему, **отбрасывая path**. Поэтому S3 endpoint с обязательным префиксом пути нельзя считать поддержанным простым указанием URL; необходимо проверить реальный endpoint будущего проекта, исправить реализацию при необходимости и протестировать операции, приватный bucket, временные ссылки и tenant isolation. При включении существующего storage `BuildStorage` проверяет bucket и при отсутствии пытается создать его при старте; это изменение внешнего ресурса и может требовать прав, несовместимых с выбранной политикой. Не подставляйте DSN Supabase в `DATABASE_URL` и не вводите неиспользуемые Supabase API keys.

## Что уже настроено и что новое

### Уже используется приложением по коду, но состояние Blitz неизвестно

`FORGECRM_ENV`, `FORGECRM_BASE_URL`, `FORGECRM_DATABASE_URL` / `DATABASE_URL`, `FORGECRM_SECRET_KEY`, `FORGECRM_COOKIE_SECURE`, `PORT`, параметры worker и остальные общие параметры из справочника. Некоторые могут не быть явно заданы и работать за счёт дефолтов или внедрения платформой. Факт готовности `/ready` сам по себе **не доказывает**, какие имена заданы и какие значения они имеют.

### Новые для операционной настройки Telegram, но не новые имена в коде

Только `FORGECRM_TELEGRAM_ENABLED`, `FORGECRM_TELEGRAM_BOT_TOKEN`, `FORGECRM_TELEGRAM_WEBHOOK_SECRET` — все три уже существуют в конфигурации. Их наличие в production неизвестно. Переменные для Mini App и Privacy Policy в проверенном проекте пока отсутствуют, так что точный будущий список нельзя добросовестно определить до реализации.

### Не нужны сейчас

- Отдельный Telegram username, bot ID, chat ID и отдельный frontend-токен в env: фактических читателей нет. Имена предполагаемых переменных намеренно не придумываются.
- URL webhook, Mini App, Privacy Policy как новые env: текущий код их не читает; точные маршруты ещё не определены. `FORGECRM_BASE_URL` уже существует, но сам эти функции не создаёт.
- Supabase URL, service-role/anon/API keys и отдельный Supabase PostgreSQL DSN: проект отсутствует и Telegram-медиа с ним не интегрированы.
- `FORGECRM_API_URL`, `FORGECRM_E2E_EMAIL`, `FORGECRM_E2E_PASSWORD`, `FORGECRM_TEST_DATABASE_URL`, `FORGECRM_TEST_REDIS_URL`, `CI`, `FACTS_COMMIT` — dev/test/CI, не нужны production Telegram.
- `RENDER_EXTERNAL_URL`, `RENDER_GIT_COMMIT` — fallback для Render, не настройка Blitz. Не добавлять на Blitz ради Telegram.
- Новые bootstrap-пароли, второй `FORGECRM_SECRET_KEY`, SMTP/OIDC/AI параметры или новая PostgreSQL только ради Telegram.

## Проверка поведения и возможные конфликты

1. `FORGECRM_TELEGRAM_ENABLED=true` без токена тихо превращается в отключённое состояние. Наличие обоих значений не доказывает, что токен валиден или бот связан с сотрудником.
2. `FORGECRM_TELEGRAM_WEBHOOK_SECRET` сейчас не защищает входящий HTTP: `VerifyWebhookSecret` не подключён к маршруту. Регистрация webhook без реализованной проверки небезопасна. Существующие `/api/v1/webhooks` — исходящие вебхуки CRM, а не вход Telegram.
3. Таблица `telegram_links` допускает конфликт ожидающих кодов из-за уникального Telegram ID `0`; потребление кода неатомарно. В развёрнутом коммите поиск получателя также не ограничен организацией. В текущей ветке последнее исправлено, но оно ещё не развёрнуто. Привязку и доставку до исправлений и PostgreSQL-тестов не использовать.
4. Мини-приложение не может безопасно авторизоваться одной передачей Telegram ID или `initDataUnsafe`. Нужны серверная проверка подписи `initData`, времени, защита от повторов и явная связка с CRM-пользователем и организацией, RBAC и тесты. URL страницы и настройки BotFather не заменяют эту реализацию. Текущий сайт использует обычную сессию и CSRF, не Telegram login.
5. Текущий API выставляет `X-Frame-Options: DENY` и `SameSite=Lax` для cookie; в nginx тоже есть `X-Frame-Options: DENY`, а CSP `frame-ancestors 'none'` сейчас работает в режиме Report-Only. Встраивание, cookie и авторизацию Telegram Web/клиентов необходимо отдельно спроектировать и проверить: не ослаблять глобально защиту без узкой политики и тестов.
6. В `internal/config/config.go` `FORGECRM_DATABASE_URL` перекрывает внедрённый `DATABASE_URL`; старый DSN может направлять API и worker не в ожидаемую БД. `PORT` перекрывает `FORGECRM_HTTP_ADDR`. `FORGECRM_BASE_URL` перекрывает Render fallback. `FORGECRM_ROLE=worker` на части API выберет неверный бинарник. Проверьте имена и области действия в Blitz, не публикуя значения.
7. `FORGECRM_SECRET_KEY` общий для компонентов и существующих зашифрованных данных. Не путать его с токеном бота и отдельным webhook secret, не менять его ради Telegram. Токен бота сейчас хранится как значение окружения, а не в зашифрованной записи приложения; требование пользовательского ТЗ о шифровании сохранённого токена требует отдельной реализации. В развёрнутой ревизии ошибка отправки оборачивает ошибку `net/http`, которая может включать URL с токеном; исправление исключения токена из этой ошибки находится только в текущей ветке, не в проверенном production-коммите.
8. Локальный frontend ветки уже скрывает создание кода, пока сервер не сообщает о доступности входящего транспорта; production использует другую ревизию и может показывать устаревший интерфейс. API в обеих версиях защищён разрешением `email.manage`, что не означает готовой модели доступа сотрудников к боту.

## Docker, compose, deployment и CI

- Корневой `Dockerfile` собирает SPA и оба Go-бинарника; API раздаёт SPA из `/app/public`. Секреты Telegram не передаются через build args и не должны попадать в frontend, образ или `VITE_`-переменные.
- Корневой `docker-compose.yml` задаёт части `api` и `worker`, а также локальную PostgreSQL 17. В Blitz используется управляемая PostgreSQL; не считать локальную compose-базу новой production-базой. `env_file` — локальный `.env`, в managed-среде переменные внедряются платформой. По замечанию репозитория Blitz может игнорировать compose `environment` и `entrypoint`: проверить в интерфейсе, что worker запускает worker, и что нужные переменные доступны именно нужным частям. Не считать это проверенным аудитором.
- `backend/Dockerfile` собирает backend-образ; `render.yaml` — конфигурация другого хоста, не доказательство конфигурации Blitz.
- `.github/workflows/ci.yml` использует отдельный PostgreSQL 17 и тестовые значения, выполняет backend/frontend/интеграционные проверки. Наличие тестовых env в CI не подтверждает production env, доступ к реальному Bot API, защиту webhook или совместимость Mini App. В рамках этого аудита CI/deployment не запускались.

## Действия в BotFather — вручную владельцем

1. Открыть **официального** `@BotFather` и убедиться, что `@ForgeCRM_AssistantBot` принадлежит нужному владельцу. При необходимости получить существующий токен безопасным способом; не присылать его в чат и не ротировать без необходимости.
2. Пока нет проверенной серверной реализации, не регистрировать webhook, не обещать пользователям рабочие команды и не включать рабочую кнопку Mini App. Регистрация webhook осуществляется через Bot API, а не простым заполнением env в BotFather.
3. После реализации и проверки владелец сможет настроить команды и кнопку/ссылку Mini App в настройках бота. Конкретный путь Mini App ещё не реализован: использовать нужно фактический публичный HTTPS URL после его появления, не угадывать его.
4. Privacy Policy должна сначала существовать как доступная публичная страница с актуальным содержанием. Её точный путь и способ публикации/ссылки в боте определяются реализованным UI и актуальными настройками Telegram, а не существующей env-переменной.
5. Когда webhook будет реализован и протестирован: зарегистрировать точный маршрут через Bot API с отдельным secret token; сервер обязан проверять `X-Telegram-Bot-Api-Secret-Token`. Не помещать Bot API token в URL вебхука, клиентский код или логи. Перед любым действием проверить актуальную документацию Telegram и избежать случайной замены существующего webhook.

Справка Telegram: [Bot API](https://core.telegram.org/bots/api#setwebhook), [Mini Apps](https://core.telegram.org/bots/webapps), [настройка ботов](https://core.telegram.org/bots/features). Во время аудита эти страницы ответили HTTP 403, поэтому их актуальное содержание и последовательность пунктов меню BotFather независимо не подтверждены.

## Действия в Blitz Cloud — вручную владельцем

1. На Environment **проверить только наличие и область действия** существующих общих параметров из таблицы, не копируя их значения в переписку или логи. Оставить существующие DSN и `FORGECRM_SECRET_KEY` без изменений. Убедиться, что оба процесса используют нужную PostgreSQL, а часть worker действительно запускает worker.
2. Сверить `FORGECRM_BASE_URL` с `https://forgecrm.forgecrm.blitz.cloud`; если уже корректно — ничего не менять. Проверить production-режим и безопасные cookie. Не выводить список всего окружения в терминал или лог.
3. **Не включать Telegram сейчас.** Дождаться реализации безопасной привязки и webhook, маршрутизации команд, автоматической доставки задач/уведомлений, ограничения тенанта, поддержки изображений и необходимых проверок на PostgreSQL 17. Текущая настройка не превращает бот в работоспособный модуль.
4. После отдельного утверждения и поставки готовой версии передать токен только тем серверным частям, которые реально его используют. Создать отдельный webhook secret локально и безопасно передать его в настройку сервера и регистрацию Telegram. Не выдавать токен frontend или компонентам, которым он не нужен. Точный набор частей и механизм хранения перепроверить по поставленной версии.
5. Перед активацией получить подтверждение тестов безопасности, привязки, идемпотентности, ограничений запроса, RBAC и доставки через существующий outbox/worker, а также плана резервного копирования. Перед изменением окружения согласовать рестарт/redeploy; после него проверить состояние без раскрытия секретов.

## Готовый список значений для Blitz Cloud

**Сейчас:** добавлять новые переменные для включения Telegram не рекомендуется; код не готов. Сверить единственное известное точное несекретное значение, и менять только если оно неверное и изменение согласовано:

```text
FORGECRM_BASE_URL=https://forgecrm.forgecrm.blitz.cloud
```

Если Telegram ещё не настроен, безопасное состояние по умолчанию — `FORGECRM_TELEGRAM_ENABLED=false`; наличие этого имени в Blitz не установлено и специально добавлять его при действующем значении по умолчанию не требуется. Не отключайте уже работающее окружение без проверки.

**После реализации, тестов и отдельного решения о включении**, владелец сможет задать на нужной серверной части:

```text
FORGECRM_TELEGRAM_ENABLED=true
FORGECRM_TELEGRAM_BOT_TOKEN=<лично скопировать реальный токен из BotFather в secret-поле>
FORGECRM_TELEGRAM_WEBHOOK_SECRET=<лично создать независимый секрет и внести в secret-поле>
```

Два значения в угловых скобках намеренно не являются готовыми значениями: их знает или создаст только владелец, и они не должны попадать в отчёт. Для реального webhook тот же второй секрет должен быть передан Telegram при регистрации, но **не до появления проверенного маршрута**. Параметры Supabase, адрес webhook, Mini App и Privacy Policy будут определены после реализации и выбора проекта; выдумывать их сейчас нельзя.
