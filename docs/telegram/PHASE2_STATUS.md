# Telegram MVP — состояние реализации

Код подготовлен в ветке `arena/5fd3022f-forgecrm`. **Интеграцию нельзя считать готовой к production**: нет подтверждённой регистрации и доступности webhook, теста в согласованном реальном чате и зашифрованного хранения bot token в настройке БД. ENV-токен остаётся только на сервере и не показывается frontend. Автоматическую регистрацию webhook, Mini App и интеграцию медиа с Supabase код не реализует. [Исторический аудит production](PRODUCTION_ENVIRONMENT.md) описывает старую ревизию, а не этот код.

## Реализовано

- Привязка: случайные 32 байта, в PostgreSQL только SHA-256, одноразовое транзакционное потребление, TTL 15 минут, блокировки и уникальность Telegram ID, отзыв и проверка активных организации, пользователя и membership. Самостоятельный выпуск и отзыв доступны авторизованному сотруднику через страницу аккаунта и CSRF-защищённые API, без разрешения `email.manage`.
- Входящий `POST /api/v1/telegram/webhook` выключен по умолчанию. При включении проверяется независимый секрет в `X-Telegram-Bot-Api-Secret-Token`, валидность Update, fail-closed rate limit, ограничение размера; команды обрабатываются только от человека в личном чате. Повторный update не повторяет CRM-операцию; ответ до подтверждения хранится зашифрованным, без исходного сообщения или кода. Перед повторной отправкой проверяются привязка, действующие права и актуальность/владелец раскрываемых задач. `/start`, `/help`, `/link`, `/tasks`, `/today`, `/task`, `/done`, `/due`; неизвестные команды получают безопасный ответ.
- Задачи ограничены непосредственным исполнителем и организацией; чтение требует `tasks.read`, изменение также `tasks.update`. Время `/today` — UTC, `/due` — RFC3339 с часовым поясом. Изменения идут через CRM, аудит и outbox, конкурирующее переназначение защищено блокировкой.
- События назначения, изменения срока и завершения проецируются в **существующие** outbox/jobs с retry/backoff. Просрочка планируется на срок; worker также находит уже просроченные существующие задачи, максимум 1000 за проход раз в минуту. Отдельная таблица — только долговечный журнал дедупликации, не очередь. Ревизия срока/исполнителя меняется при изменении или повторном открытии, что позволяет повторно установить прежний срок. Перед отправкой проверяются актуальная задача, владелец, membership, RBAC и ConsentGate.
- RU/EN PNG-карточки задания, изменения срока, просрочки и завершения из данных CRM; при ошибке изображения отправляется текст, ошибка изображения записывается без токена и ответа Telegram. Прогресс jobs и ledger фиксируют результат. `ok: true` значит принятие API, но не доставку/прочтение.
- Worker очищает истёкшие более суток коды и тела неотправленных ответов старше семи дней батчами по 1000. Update ID сохраняются для anti-replay; ledger доставки также сохраняется после очистки jobs. Их рост нужно мониторить и отдельно спроектировать безопасную политику retention.

## Конфигурация и ограничения

По умолчанию модуль выключен. Для будущего согласованного включения нужны `FORGECRM_TELEGRAM_ENABLED=true` и `FORGECRM_TELEGRAM_BOT_TOKEN` для API и worker; API дополнительно нужны `FORGECRM_TELEGRAM_WEBHOOK_ENABLED=true` и независимый `FORGECRM_TELEGRAM_WEBHOOK_SECRET` (32–256 символов A–Z, a–z, 0–9, `_`, `-`). Нужен стабильный существующий `FORGECRM_SECRET_KEY` для шифрования отложенных ответов. Не помещайте токены, webhook secret или коды в чат, Git, URL и логи. HTTPS и безопасная регистрация публичного webhook на `/api/v1/telegram/webhook` — отдельные операционные действия; приложение само Telegram не регистрирует. `linking_available` отражает только конфигурацию, не регистрацию и не сетевую доступность.

Сетевой вызов и фиксация в PostgreSQL не атомарны: при сбое после принятия сообщения Telegram, но до записи checkpoint, повторная доставка возможна. При отказе photo результат сети также может быть неопределённым до fallback. Пока Telegram отключён, события назначения не накапливаются для последующей отправки. Перед запуском нужны проверка пропускной способности, мониторинг ledger/очереди и осмысленная политика восстановления отказавших jobs.

Миграции `0032` и `0033` подготовлены, но в production не применялись. `0033` создаёт две служебные таблицы, индекс, trigger и добавляет revision к tasks; добавление столбца с UUID default может переписать и заблокировать большую таблицу. Перед отдельно согласованным развёртыванием необходимы резервная копия, проверка времени блокировок, порядка запуска API/worker и совместимости; down теряет anti-replay и метаданные и не должен выполняться без отдельного плана.

## Проверки

В disposable PostgreSQL 17.11 с `-race` проверены коды, гонки, tenant/RBAC, webhook с mock Telegram, дубль update, зашифрованный pending reply, отзыв и переназначение; worker: успешный PNG, fallback, ошибка/429 и backoff, consent/RBAC, дедупликация после удаления job, конкурентный overdue sweep и возврат к прежнему сроку. Реальных токенов и сообщений не использовали. Frontend lint/typecheck, 263 unit-теста и build, выборочные backend race/vet и extraction `crm`/`notify` выполнены локально; SQLite stub использовался только для компиляции и не является тестом SQLite. Полный backend и E2E/visual следует оценивать по CI конкретного коммита, а не по старым прогонам.

SSO не включать: [аудит Authentik/Keycloak и блокеры существующего OIDC](../security/SSO_AUTHENTIK.md). Password login сохраняется.
