# Telegram MVP — состояние Phase 2

Этот документ описывает частичную работу в ветке `arena/5fd3022f-forgecrm` после `6ac40e71b8d30d035cde8c7d24f633fe9dbcbc88`. **MVP не готов к включению и deployment.** Отчёт об окружении для исходной версии: [PRODUCTION_ENVIRONMENT.md](PRODUCTION_ENVIRONMENT.md).

## Сделано в коде

- Миграция `0032` добавляет таблицу короткоживущих challenge `telegram_link_codes`, не вторую очередь и не копию задач. Предыдущая схема конфликтовала на едином `telegram_user_id=0` для ожидающих кодов. Новые коды не используют этот sentinel; старые неактивные коды из прежней схемы больше не принимаются. Существующие привязки миграция не удаляет.
- Код содержит 32 криптографически случайных байта, в БД хранится только SHA-256; TTL 15 минут рассчитывается PostgreSQL. Выдача и потребление требуют активных пользователя, организации и membership; потребление, создание/изменение связи и аудит находятся в одной транзакции. Блокировка сериализует привязку и отзыв одного пользователя организации; глобальная уникальность Telegram ID исключает перехват уже активной привязки между аккаунтами/организациями. Отзыв инвалидирует и ожидающие коды.
- Разрешение пользователя и поиск получателя уведомлений требуют активной организации и membership. Это не заменяет проверку полномочий на каждое действие или подтверждение private chat в будущем webhook.
- Telegram transport теперь проверяет `ok` в ответе API, не считая HTTP 2xx доказательством принятия запроса; ошибка не включает тело ответа или токен. Даже `ok: true` — принятие API, а не доказательство прочтения пользователем.
- Исправлены две причины падения CI `6ac40e7`: обновлён генерируемый `project-facts.md`; проверка русского перевода различает команды вида `/link` и английскую прозу.

## Проверено локально

- PostgreSQL **17.11**, отдельная тестовая база: `go test -race -count=1 -tags=integration ./internal/testsupport/telegram_link_integration_test.go` с временным modfile для загрузки разрешённых GitHub-зеркал зависимостей. Тесты реально применили все 32 миграции к пустой тестовой схеме; проверены выдача нескольким пользователям, хеш, срок, повтор, отзыв, блокировка membership, межорганизационный конфликт и параллельное потребление одного и двух кодов. Тестовый кластер не связан с production.
- Unit tests notify: mock `RoundTripper` проверяет API accept/reject, HTTP 429/500, повреждённый ответ и отсутствие утечки токена; реальные Telegram сообщения не отправлялись. `go vet` для notify прошёл.
- Frontend lint, typecheck, 263 unit-теста и build прошли; существующие lint/runtime warnings остаются. Проверка фактов прошла; docs-check проходит с UTF-8 locale (`LANG=C.UTF-8`), в локальном POSIX locale проверка кириллического слова лицензии даёт ложный отказ.
- Это **не** полный набор PostgreSQL-интеграционных тестов всего проекта и не доказательство готовности webhook, RBAC действий, доставки или E2E Telegram.

## Не реализовано — блокирует MVP

1. Нет публичного входящего webhook: secret header не подключён к маршруту, нет проверки формата/частоты и идемпотентной обработки update, `/start`, `/help`, `/tasks` и `/today` не связаны с Telegram. Кнопка привязки остаётся скрытой. Наличие новой модели кода **не** позволяет сотруднику привязаться end-to-end.
2. Нет действий над задачами через bot, RBAC-проверок и экранов карточки из Telegram.
3. События назначения, срока и просрочки не отправляются через существующий outbox/worker; нет надёжных delivery state, retries/backoff и защиты от повторов на уровне доставки. Точно-однократная доставка через внешний Telegram API при неоднозначном результате сети сама по себе недостижима без дополнительной стратегии; необходима явно определённая семантика и тесты.
4. Нет визуальных PNG-шаблонов, `sendPhoto` и текстового fallback с журналом. Существующий `sendMessage` остаётся только транспортным примитивом.
5. Нет webhook, mock OIDC/Telegram E2E по всему пользовательскому пути и полного набора тестов RBAC/outbox/повторов. Истёкшие строки `telegram_link_codes` не имеют фоновой очистки; до использования нужен ограниченный безопасный retention/cleanup.
6. Текущий Telegram bot token берётся из среды, не хранится зашифрованной настройкой в БД, как требует пользовательское ТЗ.

Новых Telegram ENV не добавлено. Миграция в production не применялась; для любого будущего развёртывания нужны согласование, резервная копия и проверка процедуры миграций. В действующий production, секреты и Bot API изменений не вносили.
