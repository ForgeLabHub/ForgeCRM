## 1. Зачем это

Правило: **не удалять ветки без разбора.** Ветка в списке — это ещё не
доказательство, что она либо безопасна для удаления, либо содержит уникальный код.
Порядок обратный: сначала доказать, что уникального кода нет (или перенести его),
и только потом чистить. Этот отчёт фиксирует доказательства и оставляет список
веток на удаление как результат, а не как предположение.

Отдельно: в текущем наборе действий нет инструмента удаления git-веток, поэтому
этот отчёт **не утверждает**, что ветки удалены. Он утверждает, какие из них
безопасно удалить и почему.

## 2. Как получены факты

```bash
git fetch origin --prune
git rev-parse origin/main                     # b7d84b1...

# Все удалённые ветки и их положение относительно main.
for b in $(git branch -r | grep -v HEAD | grep -v 'origin/main$'); do
  echo "$b ahead=$(git rev-list --count origin/main..$b) behind=$(git rev-list --count $b..origin/main)"
done

# Является ли ветка предком main (то есть влита с сохранением коммитов).
git merge-base --is-ancestor origin/<branch> origin/main && echo MERGED || echo NOT

# Коммиты ветки, которых нет в main по patch-id (учитывая cherry-pick и rebase).
git cherry -v origin/main origin/<branch>

# Что ветка добавила относительно точки ветвления (её собственная работа).
git diff --stat $(git merge-base origin/main origin/<branch>) origin/<branch>

# Есть ли содержимое ветки в main — по файлам, а не по коммитам.
git cat-file -e origin/main:<path>            # файл существует в main?
git diff --quiet origin/main:<path> origin/<branch>:<path>   # содержимое совпадает?

# Состояние PR (включая закрытые и способ слияния).
curl -s -H "Authorization: Bearer $GITHUB_TOKEN" \
  "https://api.github.com/repos/ForgeLabHub/ForgeCRM/pulls?state=all&per_page=100"
```

### 3.2 Влиты squash-слиянием — коммитов нет, содержимое есть

Здесь `git merge-base --is-ancestor` даёт «нет», и это может выглядеть как
уникальная работа. Это ловушка: squash-слияние создаёт в `main` **один новый
коммит** с тем же содержимым, поэтому исходные коммиты ветки предками не
становятся. Проверка — по содержимому файлов.

| Ветка | PR | Доказательство |
| --- | --- | --- |
| `feat/platform-hardening` | #4 (merged) | `git cherry` показывает 5 коммитов как эквивалентные (`-`), уникальных (`+`) нет |
| `feat/multi-replica-verification` | #9 (merged) | `git cherry`: 1 эквивалентный, 0 уникальных; `scripts/multi-replica-verify.sh` присутствует в main |

Проверено по артефактам: `backend/cmd/openapi-gen/main.go` (из #4) и
`scripts/multi-replica-verify.sh` (из #9) есть в `main`.

### 3.6 Удаление выполнено

Все 17 веток, кроме `main`, удалены через API GitHub
(`DELETE /repos/{owner}/{repo}/git/refs/heads/{branch}`), по 204 на каждую. После
удаления `git fetch --prune` показывает единственную удалённую ветку — `origin/main`.

Два «уникальных» файла из PR #13 (`docker-compose.blitz.yml`,
`deploy/blitz-cloud/docker-compose.yml`) проверены перед удалением и оказались
**устаревшим дубликатом**: они собирают образ из `backend/Dockerfile` и объявляют
`version: '3.8'`, тогда как `main` собирает из корневого `Dockerfile` (чтобы образ
содержал веб-интерфейс) и документирует ровно это в `docs/deployment/blitz-cloud.md`.
Файлы не добавляли нового профиля развёртывания, а описывали старую схему сборки.
