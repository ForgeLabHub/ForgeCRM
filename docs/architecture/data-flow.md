# Потоки данных

## Синхронный запрос

```
браузер → nginx → API
  middleware: request-id → логирование → rate limit → сессия → CSRF
  → аутентификация → tenant-контекст → RBAC-проверка права
  → handler: валидация входа → use case (домен crm) → транзакция
  → ответ: стабильная схема, коды ошибок по docs/api/errors.md
```

Правила:

- **Tenant-контекст ставится до handler'а.** Ни один запрос к таблице без
  `organization_id` из контекста не выполняется; это проверяется тестами
  `internal/api/tenant_isolation_test.go` и `isolation_cases_test.go`.
- **Право проверяется на маршруте**, а не внутри бизнес-логики. Каталог прав —
  `internal/rbac`, синхронизация с миграциями — `make test-unit`.
- **Идемпотентность** для создающих операций — через `idempotency_keys`.

## Транзакции

Граница транзакции — прикладной сервис, не handler. Схема: открыть транзакцию →
выполнить доменные вызовы → записать событие в `outbox_events` **в той же
транзакции** → закоммитить. Побочный эффект (вебхук, письмо) выполняется после
коммита, воркером. Это исключает «событие без данных» и «данные без события».

## Асинхронные потоки

| Поток | Источник | Исполнитель | Гарантия |
| --- | --- | --- | --- |
| Вебхуки | `outbox_events` → `webhook_deliveries` | worker | at-least-once, повтор с бюджетом, dead letter |
| Фоновые задания | `jobs` | worker | попытки `FORGECRM_JOB_MAX_ATTEMPTS`, backoff |
| Workflow | событие, расписание, ручной запуск | worker | идемпотентный шаг, журнал в `workflow_step_runs` |
| Импорт | `import_jobs` | worker | пакетная обработка, ошибки по строкам |
| Retention | расписание | worker | dry-run по умолчанию, батчи, аудит |
| Уведомления | `email_log`, `notify` | API/worker | три различимых состояния: конфиг, связь, доставка |

## Жизненный цикл действия AI

1. Пользователь запрашивает действие.
2. Модель предлагает вызов инструмента.
3. Инструмент проверяется на допустимость для роли.
4. Деструктивное действие требует подтверждения человеком (`agent_approvals`) и,
   если настроено, второго фактора (step-up).
5. Исполнение фиксируется в `agent_runs` / `agent_actions` / `audit_log`.

Модель не имеет пути к записи в БД в обход прикладного сервиса — это правило
модуля `agent`, см. [modules/ai-mcp.md](../modules/ai-mcp.md) и
[ADR 0005](../adr/0005-hitl-agent-execution-model.md).

## Данные наружу

- Экспорт: `export_jobs`, отдаётся потоком, права проверяются как на чтение.
- Вебхуки: подписанные, с бюджетом попыток и защитой от SSRF.
- Наружу уходят только явно настроенные интеграции.
