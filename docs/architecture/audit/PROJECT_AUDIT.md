## 4. Аудит по областям

### 4.1 Go backend

- **Архитектура:** слоистая, направление `api → application → core`. `crm` — ядро;
  `importx`, `migratex`, `ai`, `events`, `notify`, `workflow`, `storage`,
  `integrations` — прикладные сервисы; `api` — композиция сверху. Ни один пакет
  не импортирует `internal/api` (проверено на графе: пусто).
- **Точки входа:** `cmd/forgecrm-api`, `cmd/forgecrm-worker`, `cmd/forgecrm`
  (конструктор), `cmd/facts-gen`, `cmd/openapi-gen`. API и worker собираются
  независимо и запускаются независимо (`FORGECRM_ROLE`).
- **HTTP API и middleware:** `internal/api` — 72 файла, по файлу на область;
  middleware в `internal/httpx` (recovery, request-id, лог, security headers,
  rate limit, CSRF).
- **Обработка ошибок:** единый конверт `httpx.WriteError`, коды ошибок.
- **Graceful shutdown:** реализован в API и worker (worker ждёт job в руке до
  `FORGECRM_WORKER_SHUTDOWN_GRACE`).
- **Наблюдаемость:** `internal/logging` (slog + центральное маскирование секретов),
  `internal/tracectx` (correlation ID), `internal/metrics` (Prometheus exposition
  без внешней зависимости).
- **Ограничения запросов:** `internal/ratelimit` с `MemoryStore` и `RedisStore`,
  режим отказа на политику, учёт `X-Forwarded-For` за доверенным прокси.

**Найденные недостатки backend:** см. `TECHNICAL_DEBT.md`. Критических нет.

### 4.2 База данных и миграции

- 39 пар `NNNN_name.{up,down}.sql`, симметричны (гейт `facts-gen`).
- Миграции встроены в бинарник (`//go:embed`), применяются при `-migrate` или
  `FORGECRM_MIGRATE_ON_START=true` (по умолчанию false).
- Владение данными: **одна схема**, общая для всех модулей — это осознанное
  следствие ADR 0001 (одна транзакция). Для микросервисной реализации это
  ключевое ограничение (см. `DEPENDENCY_MAP.md`, §«Владение данными»).
- Воспроизводимость: проверена локально на чистой БД (`integration-env.sh`,
  теги `integration`, rc=0).

### 4.3 Worker и фоновые процессы

- Очередь на Postgres (`SKIP LOCKED`), `internal/jobs`.
- Транзакционный outbox `internal/outbox` с `schema_version`, `correlation_id`.
- Retry с backoff, dead-letter — в `internal/events` (исходящая доставка) и в jobs.
- Идемпотентность — `internal/idempotency`.
- Worker обрабатывает: outbox, импорты, вебхуки, Telegram-доставку, retention,
  workflow-триггеры.

### 4.4 Docker и Compose

- `Dockerfile` (корень) собирает один образ с обоими бинарниками и статикой.
- `docker-compose.yml`: postgres + api + worker (+ redis, nginx — профили).
- `docker-compose.multireplica.yml`, `docker-compose.local.yml`.
- Healthcheck: API `/health`, Postgres `pg_isready`, Redis `redis-cli ping`.
- CI job `docker` собирает образ; `portability.yml/compose-smoke` поднимает стек.

### 4.5 API и OpenAPI

- Спецификация **генерируется** из живого роутера (`cmd/openapi-gen`), 240
  операций, гейт `openapi-check` в CI. Ручная правка запрещена и ловится.
- Контрактная таблица `internal/api/contract.go` (`APIContract`), `contract_test.go`
  держит направления «нет выдуманных маршрутов» и «нет сирот-компонентов».
- Каждый маршрут обязан объявить уровень доступа (`s.perm(...)`,
  `openapi.Anonymous`, `openapi.SessionOnly`).

### 4.6 Authentication / Authorization

- `internal/authn`: Argon2id, непрозрачные сессии, CSRF, блокировка, TOTP MFA,
  сброс пароля, шаг-ап.
- `internal/oidc`: authorization-code flow, привязка state к браузеру (cookie),
  явная привязка OIDC-идентичностей.
- Сессионные cookie: `HttpOnly`, `Secure` (по конфигу), `SameSite` (по конфигу).
- CSRF-токен присутствует; проверяется middleware.
- `internal/rbac`: 103 разрешения, 14 системных ролей; проверка на сервере в
  `requirePermission` (401 без сессии, 403 без права, отказ пишется в аудит).

### 4.7 RBAC и tenant isolation

- RBAC — данные, проверяются на сервере. Frontend **не** является защитой.
- Организационное ограничение: тесты `tenant_isolation_test.go`,
  `isolation_cases_test.go`. BOLA/IDOR-воркстрим закрыт в предыдущем цикле.
- `internal/tenantconfig`: закрытый версионный каталог настроек на организацию.

### 4.8 AI providers / tools / agents

- `internal/ai`: интерфейс `Provider` (`Name`, `Model`, `Complete`, `Healthy`);

- `internal/agent`: HITL-очередь предложений с подписанным подтверждением (ADR 0005).

### 4.9 MCP

- `POST /api/v1/mcp` говорит на JSON-RPC 2.0: `initialize`, `tools/list`,

## 6. Архитектурное противоречие, требующее решения владельца

Программа просит:

- `main` → **полноценные микросервисы**;
- `monolith` → **полноценный модульный монолит** (отдельная ветка от исходного `main`).

Код и принятые ADR говорят:

- ADR 0001 **явно и обоснованно** отклоняет микросервисы «с самого начала»;
  домен транзакционен, команда мала, эксплуатационный бюджет — один сервер.
- ADR 0002 вводит **измеримые триггеры** (T1–Tn) для выделения сервиса. Пока
  триггер не достигнут, нагрузка остаётся в монолите.
- `main` **уже** модульный монолит с обеспеченными границами и 36
  извлекаемыми модулями.

Следствия, которые нельзя обойти молча:

1. Сделать `main` микросервисным — значит **переписать `main`** и **отменить
   ADR 0001/0002**. Это большое, рискованное изменение, ломающее транзакционную
   целостность ядра (архивирование контакта + запись в аудит сейчас коммитятся
   вместе).
2. Создать ветку `monolith` от исходного `main` — значит получить ветку,
   **идентичную** `main` (потому что `main` уже модульный монолит). Это дубль.
3. Требование «не создавай фиктивные микросервисы, которые лишь проксируют в
   монолит» напрямую запрещает самый дешёвый способ «сделать вид» — и это верно:
   реальные микросервисы поверх транзакционного домена без триггеров ADR 0002
   дадут распределённые транзакции и регрессии безопасности.

**Рекомендация аудита (безопасный путь по умолчанию):**

- Сохранить `main` как **эталонный модульный монолит** (он уже соответствует
  Этапу D и большей части Этапа E).
- Выполнить **Этап E** (переносимые модули: `manifest.yaml` + `MODULE.md` +
  примеры переноса + проверка отсутствия зависимостей от ForgeCRM) — это
  наибольшая реальная ценность при минимальном риске и она не ломает домен.
- Для Этапа C (микросервисы) **не** переписывать `main` молча. Требуется явное
  решение владельца: либо (а) микросервисы как отдельная экспериментальная
  ветка/поэтапное выделение по триггерам ADR 0002, либо (б) явная отмена
  ADR 0001/0002 с принятием распределённых транзакций. См. ADR 0013 (черновик).

Пока это решение не принято, массовая миграция в микросервисы **не начата** —
как и требует правило 8 программы.
