# ForgeCRM — аудит безопасности (Этап A)

- **Дата:** 2026-11-07
- **Коммит:** `main` @ `3424b3e`
- **Метод:** чтение кода + существующие тесты безопасности + gosec/gitleaks-гейты
  CI. Реальные токены/секреты в отчёте **не приводятся**.

Итог: **критических известных уязвимостей не найдено.** Ниже — проверенные оси,
доказательства и открытые пункты (низкой серьёзности).

## 1. Аутентификация

| Ось | Состояние | Доказательство |
|---|---|---|
| Хеширование паролей | Argon2id | `internal/authn/authn.go`, `internal/secrets` |
| Непрозрачные сессии | серверные токены, не JWT | `internal/authn` |
| Session fixation | исключён: новый токен на входе и на MFA | `authn.go:12`, `authn.go:711` |
| Блокировка (lockout) | реализована | `internal/authn` + тесты |
| TOTP MFA | реализована | `internal/authn` |
| Сброс пароля | реализован | `internal/authn` |
| Шаг-ап привилегий | реализован | `internal/api/step_up_handlers.go` |
| OIDC SSO | authorization-code flow, state привязан к cookie браузера | `internal/api/oidc_handlers.go`, `internal/oidc` |

**Cookie:** `HttpOnly: true`, `Secure` из конфига, `SameSite` из конфига
(`oidc_handlers.go:41-43`). SameSite для SSO-state никогда не `Strict` (обосновано
в коде: IdP присылает обратный редирект).

**Открытый пункт (низкий):** убедиться, что `FORGECRM_COOKIE_SECURE=true`
обязателен в production-профиле; сейчас это конфигурация, а не жёсткая проверка
при старте. Проверка: `internal/config` — тест, падающий при `env=production` и
`cookie_secure=false`.

## 2. Авторизация

- RBAC — данные (`internal/rbac`, 103 разрешения, 14 ролей), проверка **на
  сервере** в `requirePermission` (`internal/api/server.go:766`): без сессии → 401,
  без права → 403, отказ пишется в аудит (`authorization.denied`).
- Frontend-скрытие элементов **не** является защитой: маршруты требуют право
  независимо от UI.
- **MCP-токен не даёт больше прав, чем владелец:** инструменты вызывают
  `crm.Service` под принципалом владельца токена; scope-энфорсмент + проверка
  принципала. Доказательство: `internal/api/mcp_integration_test.go`,
  `mcp_scenario_integration_test.go`.

## 3. BOLA / IDOR и изоляция

- Организационное ограничение — сквозное: `tenant_isolation_test.go`,
  `isolation_cases_test.go`.
- Воркстрим BOLA/IDOR закрыт в предыдущем цикле (см. коммиты интеграции); повторно
  не переделывался.

## 4. CSRF

- CSRF-токен + middleware; участвует в `internal/authn`, `internal/httpx`,
  `internal/api/server.go`. Проверка на изменяющих методах.

## 5. XSS

- React-экранирование по умолчанию; CSP-заголовок настраивается
  (`internal/api/csp_handlers.go`, `httpx.go:490-509`), есть report-only режим.
- Заголовки: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Content-Security-Policy`, `Strict-Transport-Security` (при настроенном HSTS).

## 6. SQL-инъекции

- Доступ к БД через `pgx` с параметризованными запросами; конкатенация
  пользовательского ввода в SQL не обнаружена при чтении `internal/crm`,
  `internal/api`, `internal/*`.
- Динамические фрагменты (сортировка/фильтры) идут через `httpx.SortSpec` и
  вайт-листы. Проверка: gosec-гейт + тесты.

## 7. Токены, API-ключи, MCP-credentials

- `internal/mcpcred` — учётные данные MCP; `internal/secrets` — AES-GCM keyring,
  хеширование паролей и токенов.
- Секреты маскируются в логах (`internal/logging`).
- gitleaks-скан в CI зелёный; секреты не хранятся в репозитории.
- **Открытый пункт (низкий):** политика ротации MCP-токенов — задокументировать
  срок жизни и процедуру ротации (сейчас ротация возможна, но не описана).

## 8. Вебхуки

- Подпись HMAC-SHA256 (`X-Signature-256`) + окно по времени
  (`X-Signature-Timestamp`), `internal/events/events.go:76-119`.
- Dead-letter и повторная доставка — `internal/events/delivery.go`.

## 9. Rate limiting

- `internal/ratelimit`: `MemoryStore` и `RedisStore` (атомарный Lua), режим отказа
  на политику, учёт `X-Forwarded-For` за доверенным прокси.
- Отдельная политика для Telegram-webhook (`server.go:200`).

## 10. SSRF

- `internal/netguard` — защита от SSRF для исходящих интеграций
  (`netguard_test.go`). Применяется в `internal/integrations`.

## 11. Секреты и утечки

- `.gitleaks.toml` + gitleaks в CI.
- `.env` не в репозитории (`.env.example` без секретов).
- Маскирование секретов в логах централизовано.

## 12. CORS

- Явного широкого CORS нет; frontend и API — один origin, обращение по
  относительному пути без preflight (`httpx.go:453`). Это безопасно по умолчанию.
- **Открытый пункт (низкий):** если появится кросс-доменный клиент, добавить
  явный вайт-лист origins.

## 13. Аудит

- `internal/audit` — append-only журнал; есть верификатор целостности
  (`audit_test.go`, ADR 0012).
- Записываются: входы, отказы авторизации, опасные операции, dead-letter вебхуков.

## 14. Изоляция данных (tenant)

- Единая схема с обязательным `organization_id`; изоляция проверяется тестами.
- Для микросервисной ветки потребуется разделение схем (см. TD-2) — иначе
  межсервисный доступ к данным нельзя запретить технически.

## 15. Статические проверки (CI)

| Инструмент | Назначение | Гейт |
|---|---|---|
| gitleaks | секреты в репозитории | падает при находке вне allowlist |
| govulncheck | уязвимые зависимости | падает при уязвимости |
| gosec | статический анализ | падает при находке вне `scripts/gosec-baseline.json` |

Базовая линия gosec содержит только прочитанные и признанные неэксплуатируемыми
находки (напр. безопасное сужение `int32` в `internal/audit/audit.go`).
