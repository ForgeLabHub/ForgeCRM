# Обновление установленной версии

## Порядок

1. Прочитать `CHANGELOG.md` и миграции между текущей и целевой версией.
2. Снять резервную копию: `make backup` (см. [database/backup-restore.md](../database/backup-restore.md)).
3. Проверить, что копия восстанавливается (в идеале — на тестовом инстансе).
4. Остановить worker, затем API (`make compose-down`) — так не останется
   полуобработанных заданий.
5. Обновить образы до конкретных версий (не `latest`).
6. Применить миграции: `make migrate`, затем `make migrate-status`.
7. Поднять стек, выполнить `make smoke-test`.
8. Проверить ключевые сценарии: вход, список сделок, создание записи, вебхук.

## Правила

- **Совместимость схемы.** Код новой версии обязан работать со схемой, мигрированной
  вперёд; обратная совместимость «новая схема — старый код» не гарантируется.
  Поэтому откат кода без отката схемы не поддерживается.
- **Откат** — только восстановлением резервной копии. Автоматического `down` нет:
  см. [database/migrations.md](../database/migrations.md).
- **Откат не считается бесплатным.** Решите заранее, что именно вы теряете
  (записи, созданные после копии).
- **Версии образов фиксируются** тегом и, для строгой воспроизводимости, digest.

## Проверка перед публикацией релиза

CI обязан пройти целиком, включая job `upgrade-path`, который применяет миграции
к базе предыдущей версии и проверяет, что сервис после этого работает. Релиз
публикуется только с зелёной матрицей проверок
([verification/matrix.md](../verification/matrix.md)).
