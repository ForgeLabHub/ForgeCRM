# Наблюдаемость и мониторинг

## Что уже есть

| Сигнал | Где | Назначение |
| --- | --- | --- |
| Структурные логи | stdout, `FORGECRM_LOG_FORMAT=json` | разбор инцидента по `request_id` |
| `request_id` | заголовок и логи | сквозная трассировка запроса через API и worker |
| `/metrics` | API, защищён `FORGECRM_METRICS_TOKEN` | счётчики и задержки |
| `app_logs` | таблица | журнал приложения в БД |
| `audit_log`, `security_events` | таблицы | что произошло с данными и доступом |
| `jobs` | таблица | застрявшие фоновые задания |
| `webhook_deliveries` | таблица | недоставленные вебхуки, dead letter |
| Health endpoints | API | живость и готовность |

## Минимальный набор алертов

1. API не отвечает на health-check 2 минуты.
2. Рост `5xx` выше 1% за 5 минут.
3. Очередь `jobs` растёт и не убывает 15 минут.
4. Появились записи в dead letter вебхуков.
5. Ошибки миграций или рассинхронизация версии схемы.
6. Отказ `pg_isready` или исчерпание пула соединений.
7. Всплеск `security_events` (подбор пароля, блокировки входа).

## Разбор инцидента

1. Найти `request_id` в логах по времени и пользователю.
2. Проверить `audit_log` и `security_events` по этому же времени.
3. Проверить `jobs` и `webhook_deliveries`: не является ли симптомом отставание worker.
4. Проверить метрики задержки БД — самая частая причина «медленного API».
5. Зафиксировать выводы в `docs/audit/`, если инцидент выявил архитектурную проблему.

## Чего нет (честно)

- Нет распределённой трассировки (OpenTelemetry) — `request_id` покрывает путь
  запроса, но не связывает его с асинхронной обработкой.
- Нет готовых дашбордов: метрики отдаются, их отрисовка — задача эксплуатации.
- Нет SLO/SLI, зафиксированных числом.
