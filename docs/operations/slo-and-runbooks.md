# SLI, SLO и runbooks

Это **предложенные** цели, а не измеренная история: у проекта ещё нет
эксплуатационных данных, на которых можно обосновать числа. Ниже зафиксировано,
что именно измеряется (SLI), какой сигнал для этого уже есть в коде, и какой
порог разумен как стартовая гипотеза. После первого пилота числа пересматриваются
по фактическим данным, а не подгоняются под желаемое.

## Откуда берутся сигналы

| SLI | Источник | Поле/метрика |
| --- | --- | --- |
| Доступность API | структурированный лог запросов | `status` в строке `request` |
| Задержка API | структурированный лог запросов | `duration_ms` в строке `request` |
| Доля ошибок | структурированный лог запросов | `status >= 500` |
| Глубина очереди заданий | `/metrics` и таблица `jobs` | `jobs{status="queued"}` |
| Отставание outbox | `/metrics` | `outbox_events` (непубликованные) |
| Живость воркера | `/metrics` | `workers_alive` |
| Отказы импорта | `/metrics` | `import_jobs` по статусу |
| Недоставленные вебхуки | `/metrics` | `webhook_deliveries_pending`, `webhook_deliveries_dead` |
| Задержка фоновой работы | таблица `jobs` | `finished_at - run_after` |

Метрика `/metrics` защищена `FORGECRM_METRICS_TOKEN`; её читает только система
мониторинга. Задержка и статус запроса есть в каждой строке лога `request`
(`duration_ms`, `status`), поэтому доступность и p95 считаются по логам без
отдельного счётчика в приложении.

## Предложенные цели

| SLI | Предложенная цель | Обоснование выбора |
| --- | --- | --- |
| Доступность API | 99,5% за месяц | одна инстанция на пилоте; 99,9% без резервирования недостижимо честно |
| Задержка чтения p95 | < 500 мс | обычные чтения — единицы мс; порог ловит деградацию, а не шум |
| Задержка чтения p99 | < 2 с | запас на холодный старт и тяжёлый поиск |
| Доля 5xx | < 0,5% | выше — уже инцидент, а не фон |
| `workers_alive` | > 0 | ноль означает, что очередь никто не разгребает |
| Отставание очереди p95 | < 5 мин | для пилота задания не критичны к секундам |
| Доставка вебхуков | 99% в пределах суток | ретраи с экспоненциальным backoff, dead letter после предела |

Все числа — **proposed targets**, пока не подтверждены эксплуатационными данными.
Пока цели не подтверждены, алерты (см. `monitoring.md`) важнее, чем SLO: они
работают по факту, а не по бюджету ошибок.

## Runbooks

Каждый runbook короткий: сигнал, первая проверка, действие, признак
восстановления. Никаких разрушительных операций без отдельного решения владельца.

### API недоступен

1. Сигнал: health-check не отвечает 2 минуты, либо всплеск 5xx.
2. Проверить `docker compose ps` и лог `api`: падает ли процесс, не кончился ли пул.
3. Проверить `pg_isready` и соединения к БД — чаще всего причина в БД, а не в API.
4. Проверить память и лимиты контейнера; рестарт `api` при OOM.
5. Признак восстановления: `/health` и `/ready` отвечают 200, доля 5xx падает.

### Воркер недоступен

1. Сигнал: `workers_alive = 0` две минуты, либо очередь `jobs` растёт и не убывает.
2. Проверить процесс `worker` и его лог: `shutdown signal received` означает
   плановый останов, а не сбой.
3. Проверить, что БД доступна воркеру (heartbeat пишется в БД).
4. Запустить воркер заново; при повторном падении искать `last_error` в `jobs`.
5. Признак восстановления: `workers_alive > 0`, очередь убывает.

### БД недоступна

1. Сигнал: `pg_isready` падает, ошибки соединения в логе API.
2. Проверить диск (заполнение — частая причина), затем `docker compose logs postgres`.
3. Не перезапускать БД вслепую: сначала зафиксировать состояние.
4. Признак восстановления: `pg_isready` отвечает, API проходит `/ready`.

### Очередь заданий растёт

1. Сигнал: `jobs{status="queued"}` растёт 15 минут.
2. Проверить `workers_alive` и `jobs` по `kind`: один тип может забивать очередь.
3. Посмотреть `last_error` у повторяющихся заданий — вероятен «отравленный» ввод.
4. Если причина во вводе — не отключать задания, а исправить данные; при
   необходимости снять зависшее задание через `Retry`/архив после решения владельца.

### Отставание outbox

1. Сигнал: `outbox_events` (непубликованные) растёт.
2. Проверить живость воркера: слив outbox делает он.
3. Проверить `webhook_deliveries_dead` — если растёт, внешний получатель отвергает.

### Отказ импорта

1. Сигнал: `import_jobs` со статусом ошибки, либо отчёт импорта с ошибками строк.
2. Открыть отчёт задания: он содержит строки и причины отказа построчно.
3. Исправить файл и запустить повторно — импорт идемпотентен по ключу строки.

### Неудачная миграция

1. Сигнал: API не проходит `/ready`, лог `migrations` с ошибкой, версия схемы
   расходится с ожидаемой.
2. Не запускать новые миграции поверх сломанной: сначала прочитать её `.up.sql`.
3. Проверить `schema_migrations` на «dirty»-состояние.
4. Восстановление — из бэкапа перед миграцией (`docs/operations/upgrades.md`).

### Подозрение на утечку credentials

1. Немедленно: отозвать подозрительный ключ/токен у провайдера (это действие
   владельца, не автоматики).
2. Проверить `security_events` и `audit_log` на необычные входы и изменения.
3. Проверить историю секретов через `gitleaks` — если ключ попал в коммит,
   считать его скомпрометированным и заменить, даже если коммит не опубликован.
4. Зафиксировать разбор в `docs/audit/`.

### Восстановление из бэкапа

1. Остановить API и воркер (не давать им писать в восстанавливаемую БД).
2. `./scripts/restore.sh <dump>` — восстанавливает БД и том импортов.
3. Сверить версию схемы и ключевые счётчики (см. `docs/operations/deployment.md`).
4. Запустить API (применит недостающие миграции) и воркер.
5. Признак восстановления: `/ready` 200, `workers_alive > 0`, счётчики совпадают.
