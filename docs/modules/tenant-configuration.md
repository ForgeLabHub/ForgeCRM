# Модуль: конфигурация арендатора

## 1. Назначение и границы
Хранит **собственные настройки организации**: значения, которые каждый арендатор
выбирает для себя поверх тех, что поставляет платформа. Это валюта сделки по
умолчанию, приоритет новой задачи, часовой пояс планировщика workflow.

Зачем это отдельный модуль: платформа обслуживает несколько организаций, и одна
не может выбрать значение за всех. До этого модуля такой выбор был либо зашит в
код, либо общим для всей установки.

Чего модуль **не** делает:
- не пишет в чужие таблицы и не читает их: он владеет только `tenant_settings` и
  `tenant_setting_revisions`;
- не решает, что значит значение: каталог объявляет ключ, тип и допустимые
  границы, а применяет значение тот модуль, который его читает;
- не хранит секреты. `app_settings` для этого и остаётся отдельной таблицей с
  отказом на ключ, похожий на учётные данные; здесь значения — обычные дефолты
  арендатора.

## 2. Сценарии использования
- Администратор организации задаёт валюту по умолчанию → новые сделки без явной
  валюты сохраняются в ней; сделка с явной валютой сохраняется как задано.
- Администратор задаёт приоритет по умолчанию → новые задачи и тикеты без явного
  приоритета получают его.
- Администратор задаёт часовой пояс планировщика → расписание без своего
  `schedule_timezone` сохраняется с зоной арендатора, а не с UTC.
- Аудитор с правом чтения смотрит действующие значения и историю изменений, не
  имея права их менять.
- Сброс значения → снова действует дефолт каталога, а в истории остаётся запись о
  сбросе с прежним значением.
- Отказ: неизвестный ключ → 404 (каталог закрыт, «такой настройки нет»);
  значение вне границ → 422 с указанием ключа; чужой арендатор → собственные
  значения, изоляция по `organization_id` из сессии.

## 3. Контракт
HTTP-маршруты под `/api/v1/settings` — в `docs/api/openapi.json`:

| Метод | Путь | Право |
| --- | --- | --- |
| GET | `/settings` | `tenant.settings.read` |
| GET | `/settings/catalog` | `tenant.settings.read` |
| GET | `/settings/{key}` | `tenant.settings.read` |
| GET | `/settings/{key}/history` | `tenant.settings.read` |
| PUT | `/settings/{key}` | `tenant.settings.manage` |
| DELETE | `/settings/{key}` | `tenant.settings.manage` |

Маршруты привязаны к организации вызывающего, а не к `organization_id` в пути:
назвать чужую организацию негде, потому что её берут из сессии. Публичный
Go-контракт — `internal/tenantconfig`: `Definition`, `Setting`, `Revision`,
`Service`, `Effective`/`EffectiveString`/`EffectiveInt`/`EffectiveBool`.

Интерфейс: `/admin/configuration` (`frontend/src/pages/admin/TenantSettingsPage.tsx`,
клиент `frontend/src/api/tenantSettings.ts`). Редактор строится из ответа
`/settings`, а не из списка ключей в коде: ключ, добавленный на сервере, появляется
без правки интерфейса, а неизвестный ключ не предлагается. Различие «организация
выбрала» и «дефолт платформы» читается из `has_override`, а не сравнением значений;
сохранение показывает значение из ответа сервера, а не отправленное; сброс
запрашивает подтверждение и называет удаляемое значение. Право `manage` скрывает
элементы управления, но защита — на сервере.

Собственных событий в `outbox` модуль не эмитит: изменение настройки — это
конфигурация, а не бизнес-факт. Каждое изменение пишется в аудит
(`tenant.settings.updated`, `tenant.settings.reset`) в той же транзакции.

## 4. Данные
Владеет: `tenant_settings` (текущее переопределение), `tenant_setting_revisions`
(история). Миграция: `0028_tenant_configuration` (up/down).

Модель из двух таблиц, а не одной:
- отсутствие строки в `tenant_settings` — не «настройки нет», а «действует дефолт
  каталога». Дефолты не материализуются, поэтому живут ровно в одном месте и не
  расходятся с кодом;
- `tenant_setting_revisions` — цепочка: кто, когда и на что менял значение.
  Сброс — тоже запись, с прежним значением, иначе «почему это изменилось?»
  остаётся без ответа.

Каждое значение несёт `schema_version`: значение, записанное под старой схемой,
интерпретируется, а не угадывается. Индексы — под историю по ключу, общий листинг
и retention-sweep по `created_at`.

## 5. Права
Права: `tenant.settings.read` (видеть действующие значения) и
`tenant.settings.manage` (менять). Разделены: значение задаёт дефолт, который
наследует вся организация, поэтому аудитору нужно видеть валюту чисел, не двигая
её. `manage` — только `platform_owner`, `platform_admin`, `tenant_admin`.

Изоляция: чтение и запись фильтруются по `organization_id` из principal; ключ из
пути проверяется по каталогу до обращения к БД. Отказ в правах → 403; чужой
арендатор неотличим от «настройки нет».

## 6. Зависимости
Исходящие: `database`, `audit`, `rbac` (только идентификаторы прав).
Входящие: `api` (HTTP), `wiring` (сборка), а через узкие локальные порты —
`crm` и `workflow`, которые объявляют свой интерфейс `OrgDefaults` и **не**
импортируют этот пакет. Стрелка зависимости идёт от конфигурации к домену, не
обратно: домен остаётся в неведении о том, как дефолт хранится и версионируется.

## 7. Конфигурация
Собственных переменных окружения нет. Значения живут в БД и читаются через
сервис. Каталог ключей версионируется в коде (`SchemaVersion`); неверное значение
ключа отвергается при записи, а не игнорируется при чтении.

## 8. Сборка, запуск, локальная отладка
Собирается в составе бэкенда (`make build-api`, `make build-worker`). Оба процесса
собирают сервис: API — для маршрутов, worker — чтобы созданные автоматизацией
сделки и задачи получали те же дефолты арендатора. **Оба** движка workflow тоже
получают порт: `internal/wiring` собирает движок дважды, и подключение лишь к
воркеру оставляло расписание, созданное через `POST /api/v1/workflows`, в UTC,
хотя организация выбрала другую зону. Регрессия —
`TestTenantDefaultTimezoneReachesAWorkflowCreatedOverHTTP`. Точечная отладка —
unit-тесты пакета:

```bash
cd backend && go test ./internal/tenantconfig/ -v
```

Выделяемость доказана: `scripts/extract-test/tenantconfig/setup.sh` копирует пакет в
чистый модуль с `audit`, `database`, `rbac` и `logging`, собирает его, прогоняет тесты
и smoke. Он зарегистрирован в `scripts/extract-test/modules.txt`, поэтому прогоняется
на каждом прогоне CI.

Интеграционные тесты — против реального PostgreSQL:

```bash
cd backend && FORGECRM_TEST_DATABASE_URL=... go test -tags=integration ./internal/api/ -run TenantSettings -v
cd backend && FORGECRM_TEST_DATABASE_URL=... go test -tags=integration ./internal/testsupport/ -run TenantDefault -v
```

## 10. Наблюдаемость и ошибки
Аудит: `tenant.settings.updated` и `tenant.settings.reset` в `audit_log`, с прежним
и новым значением, в одной транзакции с записью значения. История изменений
читается и после закрытия окна retention аудита.

Ошибки: `not_found` (404, ключ вне каталога), `validation_failed` (422, значение
вне границ, с ключом в `details`), `forbidden` (403, нет права). Метрики — общие
для API: задержка по маршрутам и количество 5xx.

## 11. Ограничения и критерии готовности
- Каталог закрыт: значение задаётся только для ключа из кода. Добавление ключа —
  изменение в Go и миграция при необходимости, а не запись произвольной строки.
- Модуль не конвертирует валюты по курсу: он только выбирает код валюты.
- Секреты здесь не хранятся намеренно — для них остаётся `app_settings` с
  отказом на ключ, похожий на учётные данные.
- Готовность: миграция применяется и откатывается; unit- и интеграционные тесты
  зелёные; каждый ключ каталога имеет реального потребителя (проверяется тестом).
