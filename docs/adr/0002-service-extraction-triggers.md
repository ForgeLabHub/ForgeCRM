# ADR 0002 — Измеримые триггеры выделения сервиса

- **Статус:** Принято
- **Дата:** 2026-10-28
- **Решающие:** владелец проекта, инженерный агент
- **Зависит от:** ADR 0001 (гибридная архитектура)

## Контекст

ADR 0001 держит каждую нагрузку в одном модуле и двух процессах и откладывает
выделение. «Выделим, когда заболит» — это не решение, по которому кто-то может
действовать, и именно так монолит случайно превращается в распределённую систему —
обычно во время инцидента, под давлением сроков, без измерения, которое бы это
оправдало.

Выделение имеет реальную, постоянную цену:

- Граница транзакции превращается в протокол согласованности. Доменная операция,
  которая сегодня коммитится, становится сагой с компенсирующими действиями.
- Каждому межсервисному вызову нужны свои тайм-аут, повтор, предохранитель и ключ
  идемпотентности.
- Наблюдаемость должна пересекать границу: трассировка, correlation ID и конвейер
  логов, следующий за запросом через два развёртывания.
- Две вещи для развёртывания, версионирования, резервного копирования и
  мониторинга вместо одной.
- Становится возможным расхождение версий, поэтому каждому API нужны правила
  совместимости.

Эту цену стоит платить по измеренной причине и никак иначе. Этот ADR фиксирует
причины, чтобы решение было порогом, а не делом вкуса.

## Решение

Нагрузка выделяется в собственный сервис **только** тогда, когда достигнут хотя бы
один триггер ниже и это зафиксировано в ADR, который заменяет соответствующую
часть ADR 0001. У каждого триггера есть номер, способ измерения и причина, по
которой он указывает на реальное ограничение, а не на неудобство.

### T1 — Конкуренция за ресурсы с измеренным влиянием

Использование CPU или памяти нагрузкой измеримо ухудшает задержку API, и
масштабирование API это не исправляет, потому что нагрузка конкурирует за тот же
процесс.

- **Измерение:** p95 задержки API во время репрезентативного импорта или пакета
  ИИ по сравнению с той же задержкой в покое; плюс RSS/CPU процесса для обоих.
- **Порог:** p95 задержки не менее чем вдвое выше базовой в покое, устойчиво на
  трёх прогонах, при нагрузке и API в одном процессе.
- **Почему:** это единственное, что разделение API/воркер уже не решает, потому что
  конкуренция идёт *внутри* процесса.

### T2 — Потребность в независимом масштабировании с расходящимися коэффициентами

Спрос на ёмкость нагрузки расходится со спросом API на большой устойчивый
коэффициент, так что совместное масштабирование тратит ресурсы.

- **Измерение:** необходимое число реплик для каждого, за неделю продакшн-трафика,
  выраженное как отношение.
- **Порог:** устойчивое отношение 4:1 или больше.
- **Почему:** текущее разделение уже позволяет API и воркеру масштабироваться
  раздельно. Этот триггер применяется к *третьей* нагрузке, которой нужен свой
  коэффициент.

### T3 — Жёсткое требование изоляции из непреложного ограничения

Требование безопасности, соответствия или радиуса поражения не может быть
выполнено в процессе.

- **Измерение:** конкретный контроль, который не удаётся реализовать, и почему
  изоляции в процессе недостаточно.
- **Порог:** выявленное требование без реализации в процессе.
- **Почему:** это самый сильный триггер и единственный, который может оправдать
  выделение без измерения нагрузки. Он всё равно требует ADR, потому что цена
  одинакова независимо от причины.

### T4 — Языковая или runtime-граница, которая нужна реальной нагрузке

Нагрузка действительно требует другого runtime — например, обработки недоверенных
архивов со строгими ограничениями ресурсов или численно тяжёлого преобразования.

- **Измерение:** конкретное требование и доказательство, что Go его не
  удовлетворяет.
- **Порог:** продемонстрированный отказ реализации на Go против заявленного
  предела.
- **Почему:** задача разрешает Rust для изолированной обработки недоверенных
  архивов, но только с заявленной причиной, интерфейсом, стоимостью сопровождения
  и доказательством. Этот триггер и есть та планка. «Rust быстрее» — не
  доказательство; профиль, показывающий превышение предела, — да.

### T5 — Независимый цикл релизов, требуемый внешней стороной

Нагрузка должна выпускаться по графику, который нельзя согласовать с ядром, потому
что от неё зависит внешняя сторона.

- **Измерение:** требуемый цикл и стоимость координации при его несоблюдении.
- **Порог:** задокументированное внешнее требование.
- **Почему:** редко, и стоит назвать, чтобы это не поглощалось молча.

## Что намеренно не является триггером

Это всплывает в каждом обсуждении выделения и само по себе недостаточно:

| Аргумент | Почему недостаточен |
|---|---|
| «Это отдельный домен» | Разделение доменов достигается границами пакетов и обеспечивается `internal/archtest`, без транзакционной цены. |
| «Так будет легче тестировать» | Хорошо ограниченный пакет уже тестируется изолированно. Выделение обычно усложняет тестирование, потому что интеграционным тестам теперь нужна сеть. |
| «Возможно, понадобится масштабирование» | Умозрительно. Дождитесь T2. |
| «В теории у него другой стек» | Дождитесь T4 и его доказательств. |
| «Микросервисы — отраслевая норма» | Не измерение. |

## Процесс при достижении триггера

1. Зафиксируйте измерение, а не впечатление: запрос, окно и результат.
2. Напишите ADR, в котором указано, какой триггер достигнут, интерфейс, модель
   согласованности, режимы отказа, влияние на дежурство и план отката.
3. Сначала определите контракт — версионированный API или схему событий — и
   держите реализацию в процессе за ним, чтобы выделение было изменением
   развёртывания, а не переписыванием.
4. Только затем переносите код.

## Текущая оценка

Ни один триггер не достигнут. В частности:

- Разделение API/воркер уже изолирует две крупнейшие нагрузки, поэтому остаток
  области T1 узок.
- Развёртывание по дизайну однотенантное, поэтому ни одного отношения
  масштабирования не наблюдалось (T2).
- Не выявлено требования соответствия, которое не могли бы выполнить контроли в
  процессе (T3).
- Распаковка архивов ограничена в процессе через `internal/importx/safe`, с
  лимитами на число записей, общий объём, размер записи, глубину и коэффициент
  сжатия. Ни одно измерение пока не показывает, что этих лимитов недостаточно (T4).
- Ни одна внешняя сторона не зависит от независимого цикла (T5).

**Следствие:** нагрузки импорта, ИИ, уведомлений и интеграций остаются в монолите.
К этому вернутся, когда триггер будет достигнут, с измерением, записанным здесь.

## Проверка

- ADR 0001 фиксирует архитектуру, которую изменяют эти триггеры.
- `backend/internal/archtest` сохраняет модуль извлекаемым, поэтому достижение
  триггера позже — это изменение развёртывания, а не упражнение по распутыванию.
- Этот ADR не объявляет ни одного измерения достигнутым. Когда оно появится, оно
  будет добавлено выше вместе с запросом, окном и результатом.
